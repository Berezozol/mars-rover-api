## Сверка: разбор расхождений

### Perseverance — расхождений нет
- **26 отброшенных записей** (солы 45, 61, 69, 130, 190, 448×3, 477, 544, 545×5, 640×3, 674×4, 697, 724, 814, 1834) — все 26 по логам backfill (`.backfill-perseverance-*.log`) — `Dropping duplicate upstream image`: источник отдал тот же `imageid` дважды в одном диапазоне. `received − dropped = stored` на каждом соле, поэтому 579 518 − 26 = 579 492.
  - Причина — особенность источника. Два варианта, различить без новых запросов нельзя: (а) в фиде действительно задвоены записи (дубли идут сериями соседних тайлов `…_01…_05`, это похоже на повторно принятые кадры); (б) нестабильный порядок внутри сола при `order=sol desc` и постраничной выдаче — тогда на стыке страниц тот же кадр приходит дважды, а соседний не приходит ни разу, и мы недосчитываемся до 26 снимков.
  - Проверка (нужен «ок» владельца, ~15–30 запросов): пересинхронизировать каждый из 15 солов отдельно, `uv run python -m app.cli sync --rover perseverance --from-sol S --to-sol S`. Если `stored` вырастет — верен вариант (б), и адаптеру нужен стабильный порядок (если фид умеет `order=sol desc,date_taken desc` или похожее) либо перекрытие страниц (`backend-dev`).
- **«≈589k против ≈580k»**: цифры 589k нет ни в базе, ни в журнале, ни в документах. Фактические числа: в таблице 579 492; `total_results` источника 579 518 (с 26 дублями); `total_images` 1 055 868 (с миниатюрами, их не храним); сумма `sync_runs.photos_upserted` 579 498 (+6 — тестовый запуск этапа 3 по солам 2029–2031, run 1, потом перекрыт backfill). Скорее всего 589k — опечатка в 579k.
- 67 солов без снимков — у источника по ним пусто (запрошены, ответ пустой), в том числе 2025–2030 перед последним солом 2031.

### Curiosity — внутренняя сверка чистая; 3 346 расхождений со старым API — особенность старого API
- Таблица, сводки, счётчики камер, `received` и итог источника совпадают: 791 788 везде, отброшенных нет. Сумма `photos_upserted` 793 505 больше на 1 717 = 571 + 573 + 573 — тестовые запуски этапа 3 (сол 1000; 5071–5073 дважды), их данные перекрыл backfill. Run 5 (`failed`, `fake://`) — смоук-тест, сол 0 загружен позже.
- **Старый манифест** (архив 2025-02-02): max_sol 4440, 698 717 снимков, 3 949 солов. Сверка сравнивает его с нашими полнокадровыми счётчиками (v1 Curiosity = только `full`, `LEGACY-API.md` п. 7): 312 равны, 291 у нас больше (ожидаемо — старый скрапер брал одну страницу 200), **3 346 у нас меньше — все на солах ≤ 4102**, после сола 4102 нет ни одного (`scripts/stage7_legacy_bins.py`).
  - Причина: до ~сола 4103 (февраль 2024) база старого API наполнялась прежним скрапером старого фида, и в ней лежат **все типы кадров, видимо вместе с миниатюрами**: на солах 0–1499 и 2500–3999 у большинства солов старый счётчик больше даже нашего «все типы без миниатюр» (сол 20: старый 1 046 при нашем 524 = 6 full + 518 subframe, камера одна — `MAST`, старое имя). С сола ~4103 старый API считал только `full` и больше 200 на сол не брал — это то поведение, которое описано в `LEGACY-API.md`, и там расхождений нет.
  - Это не наш баг и не дыра в загрузке (внутренняя сверка чистая, источник подтверждает 791 788). Но это **расхождение v1 с оригиналом для солов ≤ 4102**: клиент старого API видел там больше кадров (и миниатюры), наш v1 отдаёт только `full`. Решение — за владельцем: (а) принять и записать в «допустимые расхождения» `LEGACY-API.md`; (б) для Curiosity на солах ≤ 4102 показывать в v1 все типы кадров (миниатюр у нас всё равно нет, точного совпадения не будет).
  - Предложение `backend-dev`: в `reconcile.compare_legacy` для Curiosity сравнивать только солы ≥ 4103 (или сравнивать ранние солы с «все типы» и считать «у нас меньше» ожидаемым), иначе сверка навсегда остаётся красной.
- Perseverance: архивного манифеста старого API в Wayback нет — сравнение невозможно.

### Что медленно и что предлагается (решает `backend-dev`)
1. **v1 без `page` на больших солах** — SQL 27 мс, остальные ~190 мс уходят на сериализацию 4 тыс. объектов в 7–8 МБ JSON. Индекс не поможет. Предложение: собирать ответ v1 без повторной валидации `response_model` (готовый dict → `orjson`/`ORJSONResponse` или `TypeAdapter.dump_json`) и включить `GZipMiddleware` (повторяющийся JSON сжимается в разы — меньше время передачи; коэффициент не замерялся). Повторить замер после правки.
2. **v2 `count` с `camera` без `sol`** — `count(photos.id)` с JOIN `cameras`: Bitmap Heap Scan читает 80 тыс. страниц, 283 мс. Без нового индекса (`scripts/stage7_index_trial.py`, лучший из 3):
   - `count(*) … WHERE rover_id=$1 AND camera_id=$2` (камера заранее по коду) → Index Only Scan по существующему `ix_photos_rover_id_camera_id_sol`: **14 мс**;
   - или сумма из `camera_sol_counts` (уже ведётся синхронизацией; при `sample_type=full` — `full_photos`): **3 мс**. Рекомендую этот вариант.
3. **v2 `sample_type` без `sol`** — `count` через Parallel Seq Scan, 190–200 мс; список с редким или отсутствующим типом идёт по индексу сола и перебирает весь марсоход: `perseverance?sample_type=subframe` (0 строк) — 358–426 мс, `curiosity?sample_type=mixed&page=201` — 237–256 мс. Пробный индекс (внутри транзакции, откатан):
   ```sql
   CREATE INDEX ix_photos_rover_id_sample_type_sol ON photos
     (rover_id, sample_type, sol DESC, taken_at DESC, id DESC);
   ```
   | запрос | до | после |
   |---|---|---|
   | count subframe Curiosity | 201 мс, Parallel Seq Scan, read=232 963 | 53 мс, Parallel Index Only Scan, hit=15 081 |
   | список subframe Perseverance (пусто) | 358 мс, Index Scan по солу, 250 тыс. буферов | 0,05 мс, 3 буфера |
   | список mixed Curiosity, offset 20 000 | 237 мс, Seq Scan + sort | 9,6 мс |
   | список subframe Curiosity, page 1 | 0,1 мс | 0,07 мс |
   Индекс несёт `id`, поэтому текущий `count(photos.id)` тоже становится Index Only. Ориентир размера — 60–100 МБ (индекс по солу сейчас 94 МБ). Вариант без индекса — хранить счётчики по `sample_type` в `sol_summaries`, но список с редким типом всё равно останется медленным.
4. **Глубокий `OFFSET`** (не в цели, на будущее): Curiosity без фильтров, offset 700 000 — 2,7 с; MCZ_LEFT, offset 170 000 — 0,9 с. Лечится только курсорной пагинацией (изменение контракта v2 — с подтверждения владельца) или ограничением максимальной страницы.
5. `/cameras` после миграции 0004 читает `camera_sol_counts` — 4–6 мс, кандидат из ревью закрыт. Seq Scan по `sol_summaries` в манифесте (7 тыс. строк, 272 буфера, 2–3 мс) нормален.
