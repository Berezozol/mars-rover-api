## Дизайн потоковой загрузки (предложение, ничего не запускал)
Реализует `backend-dev` как команду приложения (`app.cli backfill --source rad`), не скрипт.
1. **Каталог файлов:** один раз прочитать `CHECKSUMS.TXT` (1 МБ, 1 запрос) вместо 44 листингов диапазонов; там все пути и md5. Имена файлов по солу не вычислить (в имени час и минута).
2. **Один файл за раз:** `GET` `.TXT` через общий клиент `app/sources/http.py` (stream), построчный парсер-автомат по секциям; из каждого наблюдения берутся `START_OBS_MARS`, `START_OBS_UTC`, `OBS_DURATION`, `QC`, `TOTAL_DOSE_B`, `TOTAL_DOSE_E`. Остальное пропускается без накопления. `.LBL` (1,2 МБ) **не качать**.
3. **Без диска:** поток → парсер → отбросить. md5 считать на лету и сверять с `CHECKSUMS.TXT`.
4. **Возобновление по солу:** итог сола пишется одной транзакцией (`rad_daily` + `source_file`, `md5`, `rdr_version`); при старте пропускаются солы, где md5 в БД совпадает с `CHECKSUMS.TXT`. Прерванный сол пересчитывается. Параметры `--from-sol/--to-sol`.
5. **Вежливость:** один файл за раз, пауза ≥ 1 с, общий User-Agent, ретрай один раз на 5xx/таймаут, без параллельных запросов.
6. **Свёртка:** по солу среднее `dose_b` и `dose_e`, взвешенное по `OBS_DURATION` (мкГр/ч ×24 = мкГр/сут), min/max (мкГр/ч), `n`, суммарная длительность наблюдений. Наблюдения без дозиметрии и с маркером пропуска (когда станет известен) исключаются.
7. **Ориентир по времени (скорость канала VPS не измерял):** ≈ 4850 файлов × 68 МБ ≈ 330 ГБ. При 10 МБ/с ≈ 8 с на сол (7 с + пауза 1 с): ≈ **11 часов**; при 3 МБ/с ≈ **32 часа**; при 1 МБ/с ≈ **4 суток**. Парсинг 2–4 с на сол, не узкое место. Запускать по диапазонам каталога (≈ 134 сола, ≈ 9 ГБ, 20–60 минут), ночью на VPS, тимлид запускает сам.
8. **Обновление:** релиз раз в 4–5 месяцев; синхронизация = перечитать `CHECKSUMS.TXT`, загрузить новое/изменённое (≈ 130 солов, ≈ 9 ГБ).
