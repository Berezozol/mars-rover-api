## 2. Стоимость фильтров сейчас (EXPLAIN на полном объёме)

| Запрос | План | Время |
|---|---|---|
| 2 марсохода, сол 1000-1002, `ORDER BY sol, taken_at, id DESC LIMIT 25` | Index Only Scan `ix_photos_rover_id_sol_taken_at` + top-N sort, 1 699 строк | 4,6 мс |
| Все 5 марсоходов, сол 1000-1100, сортировка `taken_at DESC` | тот же индекс, 48 209 строк | 26 мс |
| 2 марсохода, сол 1000-1100, `OFFSET 5000` | тот же, 37 635 строк | 9 мс |
| Диапазон `earth_date` (3 дня) без марсохода, сортировка `taken_at DESC` | Index Scan `ix_photos_rover_id_earth_date` без ведущего `rover_id` (проход по индексу), 2 916 страниц | **521 мс** (холодный) |
| `count(*)` за месяц по `earth_date` | Index Only Scan | 3,7 мс |
| Окно LMST 17-18 ч Curiosity (выражение над `extra`) | Parallel Seq Scan 2,2 ГБ | 134 мс (LIMIT 25) / **3,8 с** (count) |
| `min_width >= 1920` Perseverance, `count` | Parallel Seq Scan, regexp на каждую строку | **9,2 с** (холодный) |
| то же с `ORDER BY sol DESC LIMIT 25` | Index Scan по `(rover_id, sol)` с фильтром | 16 мс (при редкой ширине сканирует много) |
| `mastEl > 10` Perseverance, `count` | Parallel Seq Scan | 0,3 с (тёплый) |

Выводы: мульти-марсоход + `sol_min/sol_max` + `sort` уже дёшево на `ix_photos_rover_id_sol_taken_at` (когда `rovers` не задан — подставлять явный список всех пяти). Диапазон дат без марсохода плох из-за ведущего `rover_id` в индексе: либо всегда `rover_id IN (...)`, либо индекс `(earth_date, taken_at, id)`. Фильтры по `extra` без индекса — Seq Scan на 2,2 ГБ: 0,3-9 с, для публичной ручки недопустимо.

## 3. Индексы и колонки (оценка по 10% выборке, размеры x10)

`extra` лежит в строке таблицы (TOAST всего 1,2 МБ), выражение вычисляется на каждой строке. Рекомендация: **физические колонки**, заполняемые при записи (адаптер/`photo_meta`) и разовой пакетной заливкой по солам. `GENERATED ... STORED` с regexp перепишет 2,2 ГБ под эксклюзивной блокировкой — хуже.

| Колонка | Тип | Индекс | Размер индекса |
|---|---|---|---|
| `local_time_s` (секунды суток; шкала LMST/LTST выводится из марсохода) | `integer` | `(rover_id, local_time_s) WHERE local_time_s IS NOT NULL` | ~17 МБ (745 тыс. строк: MSL 388 тыс. + MER 342 тыс. + Ingenuity 14,5 тыс.; для Perseverance после перезагрузки ещё ~13 МБ) |
| `width`, `height` | `smallint` x2 | `(rover_id, width) WHERE width IS NOT NULL` | ~7 МБ (940 тыс. строк) |
| `mast_az`, `mast_el` | `real` x2 | `(rover_id, mast_el)` | ~33 МБ на индекс; фильтр не нужен (п. 6) |
| `(site, drive)` | есть | `ix_photos_rover_id_site_drive` 12 МБ | есть |
| `earth_date` без марсохода | есть | `(earth_date, taken_at, id)` | ~30-40 МБ |

Прирост таблицы от новых колонок ~6 байт на строку (~10 МБ с выравниванием) — пренебрежимо. Размеры индексов по выборке: lt (MER+Ingenuity, 10%) 0,9 МБ, width 0,7 МБ, mast_az/el 3,3 МБ каждый, site/drive 1,2 МБ.

Без новых колонок `min_width`/`min_height` допустимы только вместе с `rover` и узким диапазоном сол (Index Scan по `(rover_id, sol)` с фильтром, десятки мс на 1-10 солов).

## 4. «Золотой час» (LMST)

Восход/закат в LMST гуляют: на широтах Gale (4,6 ю.ш.) и Jezero (18,4 с.ш.) отклонение от 06:00/18:00 порядка 15-40 мин (наклон оси 25 градусов, эксцентриситет) [оценка, не вычислено]. Варианты:
1. Фиксированные 06:00-07:00 и 17:00-18:00: просто, но у Jezero часть золотого часа вылетает за окно.
2. Расчёт восхода по солу и широте: точнее, но нужна орбитальная модель и широта; усложняет API.
3. Расширенные окна 05:30-07:00 и 17:00-18:30.

Рекомендация: общий фильтр `local_time_min`/`local_time_max` (`HH:MM`, `min > max` = переход через полночь) и документированный пресет `golden_hour=true` = вариант 3 с пометкой «упрощение»; не вариант 2. MER — LTST (другая шкала): применять как есть, в ответе уже есть `local_time.kind`; при мульти-марсоходном запросе предупредить в `API.md`.

## 5. Поиск по близости

Путь: снимок -> `(rover_id, site, drive)` -> `rover_waypoints.lat/lon`; индекс `ix_photos_rover_id_site_drive` (index-only) уже есть. `rover_waypoints` в dev пуста, поэтому замер на синтетике: TEMP-таблица со всеми 46 313 реальными парами Curiosity+Perseverance со случайными lat/lon (квадрат 0,2 градуса), гаверсинус в SQL-функции, R = 3389,5 км.

| Запрос | Результат | Время |
|---|---|---|
| Отбор стоянок в радиусе 1 км / 5 км | 1 018 / 25 638 | 12 / 11 мс (Seq Scan по 46 тыс.) |
| `count` снимков, радиус 1 км (Memoize + index-only join) | 8 721 | 15 мс |
| `count` снимков, радиус 5 км | 234 615 | 139 мс |
| Страница LIMIT 25 по `sol DESC`, радиус 1 км | идёт по `(rover_id, sol)`, 7 976 строк до 25 нужных | 33 мс |
| то же, радиус 5 км | 278 строк | 2,6 мс |

Поиск дёшев (реально стоянок 45 тыс. у Curiosity и 1,2 тыс. у Perseverance). Риск — пустая или очень малая область: план «по `sol`» перебирает все снимки марсохода (оценка до ~1 с на 790 тыс., не измерено). Решение: отбирать стоянки в `WITH ... AS MATERIALIZED` и соединять с `photos` по `(rover_id, site, drive)`, сортируя уже отобранное. PostGIS не нужен. Реальные `rover_waypoints` в dev не загружены: нужен прогон загрузки положения (1-2 запроса к MMGIS, с разрешения владельца). Только Curiosity и Perseverance; у Curiosity 50% снимков без `site/drive` близостью не найти.

## 6. Рекомендованный набор

**Сейчас (без новых индексов):** `rovers=a,b`; `sol_min/sol_max`; `date_min/date_max` (при явном списке марсоходов; иначе добавить индекс `(earth_date, taken_at, id)`); `sort` по `taken_at`/`sol`; `site_min/site_max` (индекс есть); `fields/include`.

**Следом (колонки + индексы):** `local_time_min/max` (~17 МБ; у Perseverance только новые снимки, пока история не перезагружена); `min_width/min_height` (~7 МБ; Curiosity всегда `null`, фильтр его исключает); близость к точке (после загрузки waypoints, MATERIALIZED); `golden_hour` как пресет поверх `local_time`.

**Не делать:** фильтры по углам мачты (строки в `extra`, у MER нет, у Curiosity 49%, индексы по 33 МБ; можно отдавать значения в ответе); по вектору/кватерниону камеры и `xyz` (локальная СК без привязки); по широте/долготе снимка (источника нет).
