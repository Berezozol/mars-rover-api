## 4. «Золотой час» (LMST)

Восход/закат в LMST гуляют: на широтах Gale (4,6 ю.ш.) и Jezero (18,4 с.ш.) отклонение от 06:00/18:00 порядка 15-40 мин (наклон оси 25 градусов, эксцентриситет) [оценка, не вычислено]. Варианты:
1. Фиксированные 06:00-07:00 и 17:00-18:00: просто, но у Jezero часть золотого часа вылетает за окно.
2. Расчёт восхода по солу и широте: точнее, но нужна орбитальная модель и широта; усложняет API.
3. Расширенные окна 05:30-07:00 и 17:00-18:30.

Рекомендация: общий фильтр `local_time_min`/`local_time_max` (`HH:MM`, `min > max` = переход через полночь) и документированный пресет `golden_hour=true` = вариант 3 с пометкой «упрощение»; не вариант 2. MER — LTST (другая шкала): применять как есть, в ответе уже есть `local_time.kind`; при мульти-марсоходном запросе предупредить в `API.md`.

### EXPLAIN (ANALYZE, BUFFERS)

Запрос: `WITH stops AS (SELECT site, drive, lat, lon, LEAD(drive) OVER (PARTITION BY site ORDER BY drive) next_drive FROM rover_waypoints WHERE rover_id=..), sel AS MATERIALIZED (гаверсинус <= radius) SELECT p.id FROM sel s CROSS JOIN LATERAL (SELECT ... FROM photos p WHERE p.rover_id=.. AND p.site=s.site AND p.drive>=s.drive AND p.drive<COALESCE(s.next_drive,2147483647) [фильтры] OFFSET 0) p ORDER BY p.sol DESC, p.taken_at DESC, p.id DESC LIMIT 25 OFFSET N`. План: Seq Scan по стоянкам (0,3 мс) -> Nested Loop по `ix_photos_rover_id_site_drive` -> top-N heapsort; временных файлов нет ни в одном запросе.

Точки: P = Jezero, стоянка (site 9, drive 0) 18,43266 / 77,44137; C = Gale, стоянка (site 82, drive 2176) −4,72931 / 137,39114; пусто = 17,0 / 77,0.

Выводы по времени: > 300 мс только при радиусе, покрывающем почти весь район (P r ≥ 10, C глубокая страница при r=50) — 330-440 мс; это сортировка всех снимков района (top-N heapsort, 26 кб памяти). Фильтры камеры и сола время почти не снижают (сортировка идёт после соединения; у sol-фильтра нет доступа по стоянкам). Глубокая страница не дороже первой: top-N по OFFSET+LIMIT.

Две ловушки, которых нет в черновике (без них запрос в 5-15 раз медленнее):
1. **JIT.** Оценка стоимости > 100 000 включает JIT: +160-210 мс компиляции даже при 0 найденных строк (пустая точка 165 мс вместо 0,8 мс). Нужно `SET LOCAL jit = off` для этого запроса (или `jit=off` в настройках соединения API, если ещё не выключен: в `app/db/session.py` задан только `statement_timeout` и `max_parallel_workers_per_gather`).
2. **Форма соединения.** Обычный `JOIN sel` без `LATERAL ... OFFSET 0` даёт план «индекс по `(rover_id, sol)` + фильтр по `sel`»: 4,8 с при r=1, при r=1 у Curiosity — отмена по `statement_timeout` (5 с). Причина: оценка `sel` 236 строк вместо реальных 6-105. Нужен `CROSS JOIN LATERAL (...) OFFSET 0` (принудительный Nested Loop от стоянок). Верхняя граница `drive < COALESCE(next_drive, 2147483647)` тоже в условии индекса: без неё индекс читает хвост `drive >= s.drive` и отбрасывает 8 тыс. строк на стоянку (JIT-выключенный прогон: 296 -> 32 мс при r=0,01).

### Индексы

Новый индекс не нужен. Есть: `pk_rover_waypoints (rover_id, site, drive)`, `ix_rover_waypoints_rover_id_sol (rover_id, sol, site, drive)` (стоянки читаются Seq Scan, 708+1389 строк, ~0,3 мс; `LEAD` считается по всем стоянкам марсохода до фильтра радиуса), `ix_photos_rover_id_site_drive (rover_id, site, drive) WHERE site IS NOT NULL` — именно он и используется. Индекс по `(site, drive)` с `INCLUDE (sol, taken_at, id)` убрал бы доступ к куче, но выигрыш ограничен сортировкой 400-580 тыс. строк; не предлагаю.

### Особенности данных для текста контракта

- Дубликатов `(rover_id, site, drive)` нет (первичный ключ). На один `site` у Perseverance до 36 стоянок (в среднем 7,8), у Curiosity до 26 (11,2). `drive = 0` у 123 (C) и 91 (P) стоянок — «приращение сайта без движения»; у P 159, у C 16 стоянок с `dist_m` 0/NULL. Они дают отдельные точки с теми же координатами, что и соседние: в радиусе стоянок больше, чем реальных мест.
- Координаты `lat`/`lon` везде заполнены.
- Один снимок -> ровно одна стоянка, дублей в выдаче не бывает (диапазоны `[drive, next_drive)` не пересекаются).
- Весь регион — 5-25 км: `radius_km` 10-50 означает «всё». Для Perseverance верхняя граница 50 км практически не отличается от 10.

### Предлагаемые правки черновика 18B-3

1. Реализация: `LATERAL ... OFFSET 0`, граница `drive < COALESCE(next_drive, 2147483647)`, `SET LOCAL jit = off` (или `jit=off` для всего пула API); `count` считать тем же соединением (17-69 мс).
2. Текст: «снимок привязан к стоянке по правилу `location`; снимки, чей `site` не имеет стоянок или `drive` ниже первой стоянки сайта, и снимки без `site` не находятся (покрытие: Perseverance 99,8 %, Curiosity 49,9 % от всех снимков, 99,4 % от снимков с `site`)».
3. Границы `near`: lat −90..90, lon −180..180 — подходят; долготу 0..360 допускать не нужно (приводить `lon` по модулю 360 до −180..180 по желанию).
4. Заметить в документе: радиус ≥ 10 км охватывает весь район обоих марсоходов, дорогой случай (330-440 мс) — «радиус больше района + сортировка»; укладывается в 5 с с запасом ×10, ограничения `radius_km` не требует.

### Холодный кэш и покрывающий индекс (замер 2026-11-21, повторный)

Метод: `docker compose restart db` перед каждым запросом (пустой `shared_buffers`; кэш ОС виртуальной машины Docker сбросить нельзя, поэтому «холодный» — это холодный Postgres, диск мог частично читаться из кэша ОС, и цифры шумят). SQL берётся из репозитория (компиляция `_near_keys_query` / `_near_count_query`), в одной сессии два прогона подряд: первый — «холодный», второй — «тёплый». Сессия: `statement_timeout=5s`, `max_parallel_workers_per_gather=0`, `jit=off`. Т/О — отмена по 5 с.

Прежний вывод «≤ 10%» неверен: у запроса ключей на весь район (Perseverance r=50, Gale r=50) каждый снимок читается из кучи (149 тыс. буферов ≈ 1,2 ГБ, 68-149 тыс. `read`), и холодный прогон упёрся в 5 с (Т/О) при тёплых 0,64 и 1,5 с. `count` индекс-онли уже сейчас (1,2 тыс. буферов), его холодный прогон почти не отличается.

Индекс: `CREATE INDEX CONCURRENTLY ix_photos_near_cover ON photos (rover_id, site, drive) INCLUDE (sol, taken_at, id) WHERE site IS NOT NULL AND drive IS NOT NULL` — сборка 8,2 с, размер 79 МБ (`ix_photos_rover_id_site_drive` — 31 МБ). Нужен `VACUUM`: `VACUUM (ANALYZE) photos` падает на параллельных воркерах (`/dev/shm` контейнера 64 МБ, «No space left on device»), прошёл `VACUUM (ANALYZE, PARALLEL 0)` за 0,8 с (карта видимости 100%: 538 557 из 538 557 страниц).

| Запрос | до: холодный / тёплый, мс | после: холодный / тёплый, мс |
|---|---|---|
| keys P r=50, -sol, стр. 1 | Т/О (>5000) / 637 | 199 / 153 |
| keys P r=50, taken_at, стр. 100×100 | 550 / 441 | 199 / 152 |
| keys C (Gale) r=50 | Т/О (>5000) / 1531 | 159 / 119 |
| keys P r=1 | 216 / 77 | 41 / 29 |
| count P r=50 / C r=50 / P r=1 | 98 / 77 / 19 (тёплые 85 / 64 / 17) | 166 / 124 / 32 (тёплые 122 / 88 / 23) |
| keys P r=50 + sample_type=full | 595 / 452 | 4974 / 646 |
| count P r=50 + sample_type=full | 560 / 418 | 582 / 469 |

- Планы после: `Index Only Scan using ix_photos_near_cover`, `Heap Fetches: 0`, буферов 2,3-4,6 тыс. вместо 149 тыс. (P r=50) и 94 тыс. (C).
- Фильтры вне индекса (`sample_type`, камера, даты, `meta`) вынуждают читать кучу: планировщик берёт `Index Scan` (не index-only) и читает 152 тыс. буферов. Холодный прогон r=50 + `sample_type=full` после индекса — 4,97 с, на грани 5 с (до индекса тот же запрос в этой серии дал 595 мс, но кэш ОС был уже прогрет прежними прогонами; честная оценка риска — «до 5 с и более» для любого такого фильтра при радиусе на весь район и холодном кэше). Индекс эту проблему не решает.
- `count` после индекса чуть медленнее (166 против 98 мс): индекс шире, читает 4,8 тыс. страниц вместо 1,2 тыс.

Рекомендация: добавить покрывающий индекс (миграция `backend-dev`) и заменить им `ix_photos_rover_id_site_drive`: он обслуживает те же запросы (`site`, диапазон `drive`, поиск стоянки снимка), дублировать 31 МБ не нужно; цена — индекс 79 МБ вместо 31 МБ и чуть более дорогие запросы только по `(site, drive)`. После массовых загрузок (backfill) нужен `VACUUM`, иначе карта видимости устареет и `Heap Fetches` вернутся (autovacuum справляется с инкрементальной синхронизацией). Для комбинированных фильтров при радиусе на весь район остаётся риск Т/О на холодном кэше: варианты — лимит/ранний отказ для `near` с тяжёлыми фильтрами, повышение `statement_timeout` для `near`, либо отдельный индекс под `sample_type` (решает тимлид). Экспериментальный индекс из dev-базы удалён (`DROP INDEX CONCURRENTLY`).

### Тяжёлый запрос без `near` (холодный, один раз)

`/rovers/curiosity/photos?site_min=0&site_max=100000&sample_type=full`:
- keys (стр. 1, `-sol`): `Index Scan using ix_photos_rover_id_sample_type_sol` + фильтр по `site`, 25 строк, 4,2 мс холодный / 0,1 мс тёплый — быстрый.
- count: `Seq Scan on photos` по всей таблице (538 тыс. страниц, 1,73 млн строк, из них 139 062 подходят), холодный — Т/О > 5 с, тёплый — 2,78 с. Причина: оценка 310 741 строк (на деле 139 062), а у `site` диапазон `0..100000` не сужает выборку; индекса, дающего по `(rover_id, sample_type, site)` подсчёт без кучи, нет. Это отдельная задача для `backend-dev` (например, индекс `(rover_id, sample_type, site)` с `WHERE sample_type = 'full'` либо отказ от точного `count` для таких диапазонов).
