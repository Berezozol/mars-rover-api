# Защита от перегрузки: замеры до разработки (AC-14, AC-15)

Дата: 2026-11-21. Спецификация: `docs/proposals/overload-protection.md`. Dev-база `mars` (PostgreSQL 16, 1,73 млн снимков), только чтение и один пробный индекс (удалён). Внешних запросов нет. Скрипт: `scripts/overload_cold.py` (SQL берётся из функций репозитория, то есть тот, что выполняет API).

Метод: перед каждым запросом `docker compose restart db` (пустой `shared_buffers`; кэш ОС виртуальной машины Docker сбросить нельзя, цифры холодные для Postgres, но диск мог читаться из кэша ОС). Сессия: `max_parallel_workers_per_gather=0`, `jit=off`, `statement_timeout=15s` (чтобы измерить время, а не отмену). Один прогон на строку. Для каждой строки замерены `count` (подсчёт `total`) и запрос ключей страницы 1 (`-sol`, 25 строк).

## AC-15. Экспериментальный индекс

Индекс: `CREATE INDEX CONCURRENTLY ix_photos_near_cover_exp ON photos (rover_id, site, drive) INCLUDE (sol, taken_at, id, sample_type, camera_id) WHERE site IS NOT NULL` рядом с `ix_photos_near_cover`. Сборка 3,9 с. `VACUUM (ANALYZE, PARALLEL 0) photos` после сборки. Размер: **102 МБ против 79 МБ** (+23 МБ, +29%, в рамках оценки +15-25 МБ). Индекс удалён (`DROP INDEX CONCURRENTLY`), в базе остался только `ix_photos_near_cover`.

Условие `WHERE site IS NOT NULL` (без `AND drive IS NOT NULL`, как в черновике) допускает строки с `drive IS NULL`; на dev-базе это не помешало плану. Сверить с условием действующего индекса (в отчёте 18B — `site IS NOT NULL AND drive IS NOT NULL`) при написании миграции `0015`.

| Запрос | до: холодный / тёплый, мс | после: холодный / тёплый, мс | План после |
|---|---|---|---|
| находка 1: count Curiosity `site 0..100000` + `full` | 2426 / 975 | **81 / 46** | Index Only Scan using `ix_photos_near_cover_exp`, Heap Fetches 0, буферов 4,2 тыс. |
| находка 1: keys стр. 1 | < 1 / < 1 | < 1 / < 1 | без изменений (`ix_photos_rover_id_sample_type_sol`) |
| `near` Perseverance r=50 + `full`: count | 620 / 447 | **199 / 139** | Index Only Scan, Heap Fetches 0, 8,4 тыс. буферов |
| `near` Perseverance r=50 + `full`: keys | 655 / 481 | **223 / 168** | Index Only Scan, Heap Fetches 0, 8,4 тыс. буферов |

Замечания:
- Планировщик сам выбрал новый индекс при наличии старого, оценка строк у `count` по-прежнему завышена вдвое (315 914 против 139 062), на плане это не сказалось.
- Строка «до» для `near` + `full` (620 мс) намного лучше 4974 мс из отчёта 18B §8: тогда `sample_type` читался из кучи на холодном диске; в этой серии кучу, видимо, держал кэш ОС. Риск «до 5 с на очень холодном диске» остаётся для запросов без индекса, с индексом куча не читается совсем (Heap Fetches 0).
- Heap Fetches 0 держится только после `VACUUM` (карта видимости); на проде нужен шаг `VACUUM (ANALYZE, PARALLEL 0) photos` (без `PARALLEL 0` падает на `/dev/shm` контейнера, см. 18B).

**Вердикт: индекс делать** (решение 3.5 подтверждено). Обе цели AC-15 выполнены: Index Only Scan, Heap Fetches 0, холодный < 1 с (81 и 199-223 мс). После принятия индекса стоянки/`near` + `sample_type`/камера могут перейти в `scan_light` (камеру в `INCLUDE` покрывает тот же индекс, но отдельного замера с камерой нет `[не проверено]`; нужен до переноса строки).

## AC-13. Живая проверка под нагрузкой

Скрипт `scripts/overload_probe.py`: локальный uvicorn на dev-базе `mars`, `RATE_LIMIT_ENABLED=false`, `HEAVY_QUERY_CONCURRENCY` по умолчанию (2), `DB_POOL_SIZE=10`, `DB_MAX_OVERFLOW=5`. 60 с, 20 асинхронных воркеров гоняют 4 тяжёлые формы по кругу; параллельно каждые 200 мс лёгкая проба (v2 сол, v1 фото по солу, `/api/v2/rovers`) и выборка `pg_stat_activity` раз в 0,25 с. Внешних запросов нет.

Тяжёлые формы: `/rovers/curiosity/photos?date_min=2012-08-06&sample_type=full`; `/photos?rovers=curiosity,perseverance&sample_type=full&min_width=1&sort=-taken_at&page=100&per_page=100`; `near` Perseverance r=50 + `camera=NAVCAM_LEFT`; `near` Curiosity r=50 + `camera=MAST` + `sort=-taken_at`. (Первый прогон с `FHAZ_LEFT` дал `422` на Perseverance — такой камеры у него нет; прогон повторён, учтён второй.)

| Показатель | Результат | Ожидание |
|---|---|---|
| лёгкие запросы | 642, все `200`, **0×503** | 0×503 |
| лёгкие p50 / p95 / max | 23,6 / 31,0 / 167 мс | p95 < 500 мс |
| тяжёлые запросы | 18 066: `503` 17 898, `200` 168 | — |
| тяжёлые `200` p50 / p95 | 633 / 1868 мс | — |
| `503` p50 / p95 / max | 28,9 / 189,8 / 714 мс | < 200 мс |
| максимум соединений к `mars` | 18 (из них 3 посторонних idle-сессии до запуска, у приложения 15) | приложение ≤ 15 |

Замечания:
- Лёгкие проба не пострадала: p95 31 мс при полной забитости шлюза.
- Хвост `503`: p95 укладывается в 200 мс, но максимум 714 мс (одиночные выбросы при 20 воркерах и пробе на одном процессе, event loop клиента и сервера делит ЦПУ ноутбука). Критерий «< 200 мс» выполнен по p95, по максимуму нет; для строгого критерия нужен отдельный клиентский процесс.
- Сырой максимум 18 включает 3 соединения чужих сессий (`pg_stat_activity` по базе `mars` без фильтра по приложению: у приложения нет `application_name`). Лимит пула 10+5=15 не превышен. Предложение `backend-dev`: задать `application_name` в `connect_args`, чтобы замер был точным.

Вердикт: **пройдено** (лёгкие 0×503, p95 31 мс; 503 быстрые по p95; соединения приложения 15).
