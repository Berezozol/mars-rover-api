# Конкурент: Mars Vista API — разбор и план обгона

Дата: 2026-11-20. Объект: `github.com/james-langridge/mars-vista-api` (сайт `marsvista.dev`, API `api.marsvista.dev`).
Цель: понять, что конкурент умеет, где он впереди и где отстаёт, и уточнить этап 18 в `docs/PLAN.md`. Этот отчёт этап 18 не заменяет, а дополняет.

Метки: **[код]** — прочитано в их исходниках (ветка `main`, последний пуш 2026-10-21); **[живьём]** — проверено запросом к их сайту или API 2026-11-20; **[док]** — только их документация; **[не проверено]** — гипотеза, ниже указано, как её проверить.

## 1. Коротко

- У них **1 655 842** снимка (главная marsvista.dev, 2026-11-20) [живьём]. У нас **1 713 748** снимков четырёх марсоходов плюс 14 553 снимка Ingenuity, всего 1 728 301 (база на ноутбуке, 2026-11-20). В README и в описании репозитория у них устаревшая цифра «1.5 million».
- **v1 у них — не замена сменой хоста.** Ключ обязателен и принимается только в заголовке `X-API-Key`, а `?api_key=DEMO_KEY` получает `401` [живьём]. Пути `/mars-photos/api/v1` нет. Ответ `latest_photos` приходит под ключом `photos`, а не `latest_photos`. Неизвестный марсоход даёт `404`, а не `400 Invalid Rover Name`. Без `page` они отдают 25 снимков, а не все. `img_src` у них — средний размер, `earth_date` — дата съёмки, а не дата по формуле от сола. Подробно — в §3.3.
- **Spirit и Opportunity у них загружены один раз** в ноябре 2025 из индексов PDS. Сборщики этих марсоходов удалены из кода 2025-11-25 [код]. Ссылки построены по тому же правилу `/data/` → `/browse/` + `.jpg`, которое мы проверили на 25 снимках из 25. Значит, ссылки у них **скорее всего живые** [не проверено ключом]. У всех снимков MER у них `sample_type: "full"`, хотя среди них есть подкадры и уменьшенные. Размеров `small`, `medium`, `large` нет, полного кадра из `.img` тоже нет.
- **Фильтры v2 у них сильнее, чем у нас**: несколько марсоходов сразу, диапазоны, сортировка, местное время, «золотой час», поиск поблизости, углы мачты, `fields`/`include`. Есть также `stats`, `batch`, панорамы, `locations`, `journey`, `traverse` (GeoJSON с упрощением), заголовки `X-RateLimit-*`, Swagger, `llms.txt`, `types.ts` и коллекция Bruno.
- **Их сильные стороны вне API**: проект открыт под MIT, CI с тестами виден всем, хостинг на Railway (Амстердам), Redis, Sentry, сайт с руководствами, галереей и страницей статуса. Наши слабые места — **хостинг на домашнем ноутбуке** и **закрытый репозиторий**.
- **Главный ход**: сделать v1 действительно совместимым («сменил хост — работает», в том числе с `DEMO_KEY`) и доказать это публично. Это уже наша сильная сторона. Второй ход — закрыть отставание по v2 в порядке 18B/18C. Третий — устранить доверительные разрывы: доступность, открытость кода, свежесть данных.

### 3.2 Доступ и лимиты
- Ключ обязателен для **всех** запросов, включая v1. Без ключа открыты только `/health` и `/swagger` [код, `UserApiKeyAuthenticationMiddleware`]. Ключ читается только из заголовка `X-API-Key` [код]. `?api_key=` → `401 {"error":"Unauthorized","message":"API key required. Provide via X-API-Key header. Sign up at https://marsvista.dev ..."}` [живьём].
- Ключ выдаётся после входа на `marsvista.dev/signin`.
- Лимиты по ключу — 10 000 в час и 100 000 в сутки. Без ключа — 100 в минуту на IP, но это касается только открытых путей. Заголовки `X-RateLimit-Limit`, `-Remaining`, `-Reset` [док, код].
- Пагинация: `page`, `per_page` (по умолчанию 25, максимум 100) — одинаково в v1 и v2 [код].

### 3.3 v1 («Drop-in replacement for the archived NASA Mars Rover Photos API»)
Ручки (`swagger/v1`) [живьём]: `/api/v1/rovers`, `/rovers/{name}`, `/rovers/{name}/photos`, `/rovers/{name}/latest`, `/rovers/{name}/latest_photos`, `/photos/{id}`, `/manifests/{name}`. То есть `latest_photos` и `/photos/{id}` **у них есть**. Формулировку в этапе 18 «в v1 не видно `latest_photos` и `/photos/{id}`» нужно исправить.

Расхождения со старым API (сверено с `docs/LEGACY-API.md`, их код — `Controllers/V1/*`, `Services/PhotoQueryService.cs`):

| Поведение старого API | Mars Vista | Мы | Последствие для клиента старого API |

| Префикс `/mars-photos/api/v1` (адрес `api.nasa.gov`) | нет (`401` до маршрутизации, в swagger пути нет) [живьём] | есть | Смены хоста недостаточно, нужно менять и путь |

### 3.4 v2
Формат, похожий на JSON:API: `{"data":[{"id","type","attributes":{...},"relationships":{...}}],"meta","pagination","links"}`. **Без `include=rover,camera` объект `relationships` пустой, и по снимку не понять, каким марсоходом и какой камерой он снят.** Их документация прямо советует всегда передавать `include` [док]. Ошибки — RFC 7807, `400` [док]. Есть `?format=camelCase`: middleware перекодирует JSON уже после ответа [код].

| Ручка | Что делает [док, код] | У нас |
|---|---|---|

### 3.6 Данные
- **Всего**: 1 655 842 [живьём]. Разбивки по марсоходам без ключа нет. Её даст `GET /api/v2/photos/stats?group_by=rover` (§7).
- **Свежесть**: на их главной последние снимки Curiosity — сол 5 079 от 19.11.2026 [живьём]. В нашей базе на ноутбуке последний снимок Curiosity — сол 5 077 от 17.11.2026. Нужно проверить `/health/sync` у нас в продакшене (§6, ход Х4).
- **Curiosity** — фид `raw_image_items` с `condition_2={sol}:sol:in`. Сборщик ходит по страницам до `total` [код]. Это правильно.
- **Perseverance** — фид `rss/api/?feed=raw_images&category=mars2020` с `&sol={sol}&num=100&page=N`, без `order`. Остановка — когда на странице меньше 100 снимков [код]. По нашей проверке 2026-11-17 параметр `&sol=` у этого фида **игнорируется** (`DATA-SOURCES.md`, строка про `m2020/sol_2029.json`). Если это так и у них, то на каждый сол они выкачивают весь фид и раскладывают снимки по полю `sol` каждого снимка. Тогда сборщик медленный, а стыки страниц без стабильного порядка теряют снимки — это вариант (б) из нашего `stage7-report.md` [не проверено].
- **Окно догрузки**: 14 солов назад от текущего (`LookbackSols: 14`). Снимки, которые NASA добавит в более старые солы, не попадут в базу [код]. Сол 0 инкремент не берёт (`Math.Max(1, …)`) [код].
- **Spirit и Opportunity**: разовый импорт `edrindex.tab` из `planetarydata.jpl.nasa.gov/img/data/mer/...` (2025-11-15/16), дедупликация только по `PRODUCT_ID`. Миниатюры удалены отдельной миграцией: Opportunity −353 тыс., Spirit −186 тыс. [код]. Ссылка — `.../browse/solNNNN/edr/<FILE>.jpg`, то же правило, по которому у нас 25 из 25 снимков вернули `200 image/jpeg` → **ссылки скорее всего живые** [не проверено ключом]. Все снимки MER помечены `sample_type: "full"`, хотя среди них есть `ESF` (подкадры) и `EDN` (уменьшенные). `small/medium/large` пустые. Полного кадра нет: browse-JPEG маленький.
- **Метаданные**: полный ответ NASA хранится в JSONB, отсюда их «100% metadata preservation». Фильтр по `site` идёт по выражению `raw_data->>'site'` с индексом [док].

## 4. Где они впереди и где уступают

### Впереди
1. **Фильтры v2 по многим марсоходам сразу** и сортировка. Это главная функциональная разница, она закрывается в 18B.
2. **Аналитика и выборки**: `stats`, `batch`, панорамы, `traverse` с упрощением и сегментами.
3. **Упаковка для разработчиков**: Swagger, руководства, `types.ts`, Bruno, `llms.txt`, заголовки `X-RateLimit-*`, ошибки в RFC 7807. Частично закрывается в 18A и 18D — 18A уже в работе: в рабочем дереве есть `app/api/llms.py`, `docs/openapi.json`, `examples/`.
4. **Доверие к инфраструктуре**: облачный хостинг вместо ноутбука, открытый код под MIT, CI с бейджем, Sentry, страница статуса.
5. **Свежесть Curiosity**: на дату проверки они впереди на 2 сола (см. §3.6).

### Уступают
1. **v1 — не замена** (таблица в §3.3). Это наш главный козырь: у них ни один клиент старого API не заработает без правок кода.
2. **Ключ и регистрация обязательны.** У нас ни того, ни другого.
3. **Spirit и Opportunity хуже**: неверный `sample_type`, нет размеров, нет полного кадра. У нас — дедупликация по кадру, честные `full/subframe/downsampled` и полный кадр через `/image?size=full` (этап 9a).
4. **Данные новых солов**: окно в 14 солов против нашего перекрытия и автодогрузки дыр, подозрение на `&sol=` у Perseverance, нет сверки итогов с источником. У нас есть `reconcile` и сверка 579 518 = `total_results`.
5. **Нет Ingenuity, образцов, RSS, соседей снимка, `nearest_sols`**.
6. **Неудобства v2**: без `include` снимок «безымянный»; `?format=camelCase` перекодирует JSON уже после ответа; `total_count` берётся из кэша счётчиков и может быть устаревшим; открытый N+1 в `stats` и манифесте (#14).
7. **Атрибуция**: у нас `credit` — в каждом снимке с партнёрами (Cornell, LANL/CNES/IRAP и др.). У них — общий `credit` в атрибутах и подпись в подвале сайта.

## 7. Что проверить с ключом владельца (18E)

Ключ заводит владелец. Нужно примерно 20 запросов, не чаще 1 в секунду, заголовок `X-API-Key`.

1. **Разбивка по марсоходам**: `GET /api/v2/photos/stats?group_by=rover` → сравнить с нашими 791 788 / 579 518 / 217 615 / 124 827.
2. **Потери Perseverance**: `GET /api/v2/photos/stats?group_by=sol&rovers=perseverance&sol_min=440&sol_max=550` → сравнить по солам с нашим `sol_source_counts`, особенно 448, 545, 640 и 674, где мы видели дубли на стыках. Расхождение больше 0 — подтверждение.
3. **Свежесть Perseverance**: `GET /api/v2/photos?rovers=perseverance&sort=-sol&per_page=1` → `sol` против нашего `max_sol`.
4. **Живые ссылки MER**: `GET /api/v2/photos?rovers=spirit&sol_min=1&sol_max=1&per_page=5` и то же для Opportunity на солах около 5000. Затем `HEAD` на 5 значений `images.full` каждого марсохода (это запросы к `planetarydata.jpl.nasa.gov`, а не к ним) → ожидаем `200 image/jpeg`.
5. **`sample_type` MER**: `GET /api/v2/photos/stats?group_by=camera&rovers=opportunity` и выборка по `sample_type=Subframe` → ожидаем 0.
6. **Скорость**: `GET /api/v2/photos/stats?group_by=camera` и `/api/v2/rovers/curiosity/manifest` (места из #14), без кэша — с уникальным `sol_max`; замерить время.
7. **v1 со старым клиентом**: `GET /api/v1/rovers/curiosity/photos?sol=1000` (без `page`) с ключом в заголовке → ожидаем 25 снимков вместо 1 000+.
