## 0. Цель, границы, критерий

**Входит:**
- учётные записи по e-mail и ключи к ним (в базе только хэш), самостоятельная выдача через подтверждение e-mail, управление своими ключами по ключу, удаление учётной записи;
- два уровня доступа: без ключа — лимит по IP (урезанный), с ключом — расширенный лимит по учётной записи; цена ответа (размер v1, тяжёлые поиски) одна для всех;
- ответы на неверный, отозванный ключ и заблокированную учётную запись в форматах v1 и v2;
- admin: поиск учётных записей, блокировка, отзыв ключей, выдача ключа вручную, удаление, счётчики использования по дням;
- отправка писем через SMTP внешнего провайдера (выбор провайдера — владелец, раздел 10), вычистка ключей из логов приложения и Caddy, текст о данных для `/developers` и страницы интерфейса.

**Не входит:** платные уровни, OAuth и пароли, капча (заготовка решения — ADR-6), список одноразовых доменов из внешнего источника, журнал отдельных запросов по ключу, ключи для интерфейса Sol Index (он остаётся анонимным), распределённый лимит (процесс один).

**Готово, когда:** запрос без ключа получает урезанный лимит по IP, с действующим ключом — расширенный лимит по учётной записи, отозванный ключ и заблокированная учётная запись — понятную ошибку в формате своей версии; цена больших ответов и тяжёлых поисков одинакова для обоих уровней; ключ можно получить по e-mail без участия владельца, а владелец может найти и заблокировать учётную запись.

Предлагаю делить на два подэтапа, чтобы не ждать провайдера почты (вопрос В1):
- **20A** — модель, ключи, уровни и ошибки, admin (включая ручную выдачу), логи, контракт; AC-1…AC-19, AC-29…AC-33;
- **20B** — самостоятельная выдача по e-mail, кабинет по ключу, письма, экраны интерфейса, текст о данных; AC-20…AC-28, AC-34…AC-36.

## 1. Факты

- Лимит сейчас: ASGI-прослойка `RateLimitMiddleware` (`app/api/ratelimit.py`), один `RateLimiter` на все ключи с окнами `RATE_LIMIT_PER_MINUTE`=60 и `RATE_LIMIT_PER_HOUR`=2000, `RATE_LIMIT_CONCURRENT`=4 (`app/main.py:151`, `app/core/config.py:123-132`). Ключ лимита — `client_key(scope)`: IP, IPv6 по `/64`.
- Доплата за размер v1 — `ResponseSizeMiddleware`, списывает `limiter.charge(client_key(scope), cost - 1)` (`app/api/ratelimit.py`, конец класса): сейчас она берёт IP заново, а не ту личность, по которой считался запрос.
- Тяжёлые поиски — `HeavyQueryGate(limit, per_client=1)` (`app/core/overload.py`), клиент передаётся из роутеров v2 `photos.py` и `rovers.py`.
- `api_key` во всех ручках v1 и v2 принимается и игнорируется (`API.md:15`, `LEGACY-API.md:22`); значение `api_key` из строки запроса уже вычищается из логов приложения (`app/core/logging.py:56-71`).
- Caddy на VPS пишет журнал доступа в JSON и удаляет заголовки `X-Admin-Token`, `Authorization`, `Cookie` (`deploy/vps/Caddyfile:35-48`), а строку запроса (`request>uri`) пишет целиком: `?api_key=` клиентов (сейчас — ключи api.nasa.gov) уже попадает в журнал Caddy.
- Admin на VPS снаружи закрыт (Caddy отвечает `404` на `/api/v2/admin*`), доступ — через SSH-туннель к `127.0.0.1:8000`.
- Процесс приложения один (`Dockerfile:90`): счётчики лимита и кэш ключей в памяти процесса корректны.
- CORS: только `GET`, `allow_headers=["*"]` (`app/main.py:164-165`). Интерфейс и API отдаются одним приложением на `solindex.net` и `api.solindex.net`: запросы интерфейса — с того же источника, CORS для них не нужен.
- `Settings.public_base_url` уже есть (`app/core/config.py:117`) — годится для ссылок в письмах.
- Ключи старого шлюза api.nasa.gov — 40 латинских букв и цифр, плюс `DEMO_KEY` (`LEGACY-API.md:140`); шлюз принимал ключ и в заголовке `X-Api-Key` (api.data.gov) `[не проверено по коду старого проекта; в фикстурах нет — проверка не нужна, решение ADR-3 от этого не зависит]`.
- Сколько запросов в минуту делает интерфейс Sol Index при обычной работе — `[не проверено]`; от этого зависит, можно ли урезать минутное окно без ключа (вопрос В2, задача `frontend-qa` в разделе 7).
- Цены и бесплатные квоты почтовых провайдеров в разделе 5 — по моим знаниям, в сеть я не хожу; перед выбором владелец сверяет их на сайтах.

## 3. Решения

1. **Ключ привязан к учётной записи по e-mail**, у записи до `API_KEY_MAX_PER_ACCOUNT` (2, решение владельца 2026-11-22) действующих ключей — для смены без простоя: выпустил новый, перевёл клиентов, отозвал старый. Лимит считается **по учётной записи**, не по ключу: обход лимита выпуском ключей не работает.
2. **Формат ключа `si_` + 32 символа base62** (~190 бит случайности, `secrets`). Приставка отличает наш ключ от ключей api.nasa.gov, которые старые клиенты v1 уже шлют: чужой формат в `api_key` по-прежнему игнорируется (ADR-3). Ключ виден только в ответе выдачи.
3. **В базе — SHA-256 ключа** (без соли и «перца»: при 190 битах случайности подбор по хэшу бессмыслен, а медленный хэш сделал бы каждый запрос дорогим). Для отображения — `prefix` (`si_` + 8 символов).
4. **Проверка ключа — в прослойке лимита**, до роутера: она решает, каким счётчиком считать запрос. Найденная личность кладётся в `scope["mars.rate_identity"]` и используется доплатой за размер v1 и `HeavyQueryGate`, чтобы все три механизма считали одного и того же клиента.
5. **Кэш ключей в памяти** (TTL `API_KEY_CACHE_SECONDS`=60, до 10 000 записей, LRU), включая отрицательные ответы. Отзыв и блокировка через приложение сбрасывают кэш сразу.
6. **Счётчики использования агрегируются в памяти** и раз в `API_KEY_USAGE_FLUSH_SECONDS` (60) пишутся в `api_key_usage_daily` одним `UPSERT` (задача APScheduler), там же обновляется `last_used_at`. При падении процесса теряется не больше минуты счётчиков — это статистика, не биллинг.
7. **Уровни (предложение, числа — вопрос В2):**

   | | без ключа (по IP) | с ключом (по учётной записи) |
   |---|---|---|
   | в минуту | 60 (как сейчас) | 120 |
   | в час | 1000 (было 2000) | 10 000 |
   | одновременно | 4 | 8 |
   | тяжёлые поиски одновременно | 1 | 1 |
   | цена ответа v1 по размеру | 256 КиБ сжатого / 1 МиБ несжатого = 1 запрос | то же |

   Минутное окно без ключа не урезаю, пока не измерено, сколько запросов делает интерфейс Sol Index (он анонимный); урезан часовой бюджет — он и отделяет «попробовать» от «выкачивать». Тяжёлые поиски не расширяю: место на сервере одно на всех (решение владельца в `PLAN.md`).
8. **Неверный ключ — ошибка, а не переход к анонимному уровню** (кроме чужого формата в `api_key`, ADR-3): отозванный ключ должен давать понятную ошибку. Неудачные попытки считаются по IP, как у admin: после `API_KEY_AUTH_MAX_FAILURES` (20) за `API_KEY_AUTH_WINDOW_MINUTES` (15) запросы с ключом с этого IP получают `429` до конца окна. Каждая неудачная попытка списывается и с лимита IP.
9. **Самостоятельная выдача без паролей**: письмо со ссылкой → подтверждение кнопкой → ключ один раз. Управление своими ключами (список, новый, отзыв, удаление записи) — по действующему ключу. Потерял все ключи — снова запрос по e-mail (та же запись, `revoke_existing` при лимите).
10. **Ссылка в письме ведёт на экран интерфейса с токеном во фрагменте** (`#token=`): фрагмент не уходит в журналы сервера и в `Referer`, а почтовые сканеры, открывающие ссылки, не тратят токен — он расходуется только `POST` по кнопке. Адрес ссылки — только из `PUBLIC_BASE_URL`, не из `Host` (подмена хоста в письмах).
11. **Ручки выдачи и кабинета — только с того же источника**: CORS остаётся `GET` (+ заголовок `X-Api-Key` для `GET` с других сайтов), запросы изменения требуют `Content-Type: application/json` — с чужих сайтов они упираются в предзапрос CORS (защита от CSRF без токенов).
12. **Письма — через SMTP провайдера**, стандартной `smtplib` в `asyncio.to_thread` (без новой зависимости), с таймаутом 10 с. Провайдер меняется настройками. Письмо — простой текст на английском, без отслеживания открытий и переписывания ссылок (у провайдера выключить).
13. **IP при регистрации не храним**: счётчики регистраций по IP — только в памяти. Для отслеживания злоупотреблений хватает e-mail, счётчиков использования и блокировки.
14. **`API_KEYS_ENABLED`** (по умолчанию `false` до выкладки) — выключатель: без него поведение как до этапа (AC-19); позволяет выложить код и включить уровни отдельным решением.
15. Admin-ручки ключей — в том же `X-Admin-Token` и на VPS снаружи закрыты Caddy, как остальные admin-ручки.

### 4.1. `API.md`, «Общие правила v2» — замена пункта про `api_key`

- **Ключ API (этап 20).** Ключ необязателен: без ключа действует лимит по IP, с ключом — расширенный лимит учётной записи (см. «Ограничение частоты»). Ключ — строка `si_` и 32 латинские буквы и цифры. Передаётся заголовком `X-Api-Key` (рекомендуется: не попадает в журналы прокси и историю браузера) или параметром `api_key`. Если есть оба — действует заголовок, параметр не смотрится. Значение `api_key` не нашего формата (например, ключ api.nasa.gov или `DEMO_KEY`) игнорируется — запрос идёт без ключа; значение заголовка `X-Api-Key` не нашего формата → `401 invalid_api_key`. Неверный, отозванный ключ и ключ заблокированной учётной записи не переводят запрос на уровень без ключа — ответ ошибкой.
- Таблица ошибок, новые строки:

  | Код | `code` | Когда |
  |---|---|---|
  | 401 | `invalid_api_key` | ключ нашего формата не найден или заголовок `X-Api-Key` не нашего формата |
  | 401 | `api_key_revoked` | ключ отозван |
  | 401 | `api_key_required` | ручка кабинета (`/api/v2/account*`) без ключа |
  | 403 | `account_blocked` | учётная запись ключа заблокирована |
  | 400 | `invalid_token` | токен подтверждения не найден, использован или истёк |
  | 409 | `key_limit_reached` | у учётной записи уже `API_KEY_MAX_PER_ACCOUNT` действующих ключей |
  | 415 | `unsupported_media_type` | `POST` ручек ключей без `Content-Type: application/json` |
  | 503 | `mail_unavailable` | письмо отправить нельзя (дневной предел или сбой почты); `Retry-After` |

  Пример: `{"error": {"code": "api_key_revoked", "message": "API key has been revoked", "details": null}}`. У всех — `Cache-Control: no-store` и `X-RateLimit-*` лимита по IP.

### 4.2. `API.md`, новый раздел «Ключи API» (после «Admin»)

Ручки есть, только если `API_KEYS_ENABLED=true`; ручки выдачи (`/keys/*`) — ещё и если настроена почта (`SMTP_HOST`), иначе `404`. Все ответы `Cache-Control: no-store`, в лимите частоты — как обычные запросы.

#### `POST /api/v2/keys/requests`
Тело `{"email": "user@example.org"}`: адрес до 254 символов, ровно один `@`, без пробелов, домен с точкой; хранится в нижнем регистре. Отправляет письмо со ссылкой подтверждения (действует `KEY_TOKEN_TTL_MINUTES`, 30 минут, одноразовая). Ответ одинаков для нового и известного адреса: `202 {"status": "sent"}`. На адрес заблокированной записи и сверх 5 запросов на адрес за сутки письмо не отправляется, ответ тот же. Больше 5 запросов с одного IP за час → `429 rate_limited`. `422 validation_error` · `415` · `429` · `503 mail_unavailable`.

#### `POST /api/v2/keys/confirm`
Тело `{"token": "TOKEN_FROM_LINK", "revoke_existing": false}`. Создаёт учётную запись (если её нет) и выдаёт новый ключ:
```json
{
  "key": "si_3fK9xQ2mL7pZ0aB4cD8eF1gH5jK6nR2s",
  "key_info": {"id": 41, "prefix": "si_3fK9xQ2m", "created_at": "2026-12-01T10:00:00Z", "last_used_at": null, "revoked_at": null},
  "account": {"email": "user@example.org", "created_at": "2026-12-01T10:00:00Z"}
}
```
Ключ показывается только здесь; восстановить его нельзя — только выпустить новый. `201` · `400 invalid_token` · `403 account_blocked` · `409 key_limit_reached` (при `revoke_existing: true` все действующие ключи отзываются и выдаётся новый) · `415` · `422`.

#### `GET /api/v2/account`
Заголовок `X-Api-Key` (или `api_key`). Ответ:
```json
{
  "email": "user@example.org",
  "status": "active",
  "created_at": "2026-12-01T10:00:00Z",
  "keys": [{"id": 41, "prefix": "si_3fK9xQ2m", "created_at": "2026-12-01T10:00:00Z", "last_used_at": "2026-12-03T08:12:00Z", "revoked_at": null}],
  "usage": {"today": 312, "last_30_days": 10450},
  "limits": {"per_minute": 120, "per_hour": 10000, "concurrent": 8}
}
```
`keys` — действующие и отозванные за 30 дней, новые первыми; `usage` — запросы по UTC-суткам, с задержкой до минуты. `401 api_key_required | invalid_api_key | api_key_revoked` · `403 account_blocked`.

#### `POST /api/v2/account/keys`
Без тела. `201` — объект как у `/keys/confirm` без `account`. `409 key_limit_reached`.

#### `DELETE /api/v2/account/keys/{id}`
Отзывает ключ своей учётной записи (можно и тот, которым сделан запрос). `204` · `404 not_found` (нет такого ключа у этой записи).

#### `DELETE /api/v2/account`
Удаляет учётную запись, все её ключи и счётчики безвозвратно. `204`.

### 4.3. `API.md`, «Admin» — новые ручки (этап 20)

- `GET /api/v2/admin/accounts?q=&status=&page=&per_page=` — `q` (до 254 символов): часть e-mail без учёта регистра или префикс ключа (`si_…`); `status` — `active|blocked`; `per_page` 1–100, по умолчанию 25; новые первыми. Элемент: `{"id", "email", "status", "created_at", "verified_at", "blocked_at", "block_reason", "active_keys", "requests_30d"}`.
- `GET /api/v2/admin/accounts/{id}` — элемент + `keys` (с `revoke_reason`) + `usage_daily`: `[{"day": "2026-12-03", "requests": 312, "rejected": 4}]` за 30 дней.
- `POST /api/v2/admin/accounts` `{"email", "note"}` → `201` как `/keys/confirm` (ключ вручную, без письма; запись сразу `verified_at`); адрес занят → выдаётся ключ существующей записи; `409 key_limit_reached`.
- `POST /api/v2/admin/accounts/{id}/block` `{"reason"}` (до 500 символов) → `200` элемент; `POST .../unblock` → `200`.
- `POST /api/v2/admin/keys/{id}/revoke` → `200` ключ (`revoke_reason = 'admin'`).
- `DELETE /api/v2/admin/accounts/{id}` → `204` (удаление по просьбе).
- Ошибки — как у остальных admin-ручек (`401`, `404 not_found`, `422`).

### 4.4. `API.md`, «Ограничение частоты» — замена пунктов про ключ лимита

- Ключ лимита: без ключа API — IP клиента (как раньше, IPv6 по `/64`); с действующим ключом — **учётная запись** ключа (все её ключи делят один бюджет, IP не важен).
- Без ключа: `RATE_LIMIT_PER_MINUTE` (60), `RATE_LIMIT_PER_HOUR` (2000), `RATE_LIMIT_CONCURRENT` (4). С ключом: `RATE_LIMIT_KEY_PER_MINUTE` (120), `RATE_LIMIT_KEY_PER_HOUR` (10 000), `RATE_LIMIT_KEY_CONCURRENT` (8). `X-RateLimit-*` описывают окна того уровня, по которому посчитан запрос.
- Размер ответов v1 и тяжёлые поиски стоят одинаково на обоих уровнях; доплата списывается с того же счётчика, что и сам запрос; тяжёлый поиск — не больше одного одновременно на IP без ключа или на учётную запись с ключом.
- Неверный или отозванный ключ: после `API_KEY_AUTH_MAX_FAILURES` (20) таких ответов с одного IP за `API_KEY_AUTH_WINDOW_MINUTES` (15) все запросы с ключом с этого IP получают `429 rate_limited` с `Retry-After` до конца окна; ключ не сверяется. Неудачная попытка списывается и с лимита IP.

**Ломает ли клиентов.** Клиенты без ключа теряют половину часового бюджета (2000 → 1000) — заметно только тем, кто выкачивает много; минутный лимит прежний. Клиенты, шлющие ключи api.nasa.gov, ничего не замечают. Ранее игнорируемое `?api_key=` в v2 с значением нашего формата теперь проверяется — до этапа таких ключей не существовало.

## 5. ADR

**ADR-1. Где хранить ключ.** (a) хэш SHA-256 в базе — быстро, утечка базы не раскрывает ключи; (b) bcrypt/argon2 — защищает слабые секреты, но ключи сильные, а цена — десятки миллисекунд на промах кэша и новая зависимость; (c) HMAC с секретом из `Settings` — плюс к (a) только при утечке базы без утечки настроек, минус — ещё один секрет и невозможность сменить его без перевыпуска всех ключей. **Рекомендую (a).**

**ADR-2. По чему считать лимит с ключом.** (a) по ключу — обход выпуском ключей; (b) по учётной записи — обход только новыми адресами, а их сдерживают лимиты регистрации; (c) по ключу и по IP одновременно — ломает клиентов за общим NAT и облачные задачи с меняющимися IP. **Рекомендую (b).**

**ADR-3. Как читать ключ.**
- v1 `api_key`: проверять всё → ломает переехавших клиентов, которые шлют ключ api.nasa.gov (их большинство: старый адрес требовал ключ); игнорировать чужой формат → совместимо. **Чужой формат игнорировать.**
- v2: (a) только заголовок — чище, но `?api_key=` уже принят с 18A и удобен в браузере; (b) заголовок и параметр, заголовок главнее. **Рекомендую (b)**, в документации советовать заголовок. Заголовок v2 — строгий (новая поверхность, совместимость не нужна; опечатка видна сразу); `X-Api-Key` в v1 — как `api_key` (шлюз api.data.gov принимал и заголовок).

**ADR-4. Коды ошибок v1.** (a) `403` с телом `{"errors": "..."}` — тот же код, что у шлюза api.nasa.gov, форма тела — наша обычная для v1; (b) `401` — правильнее по HTTP, но старые клиенты на `401` от этого API не рассчитаны. **Рекомендую (a)**, новыми строками таблицы расхождений. В v2 — `401` (ключ неверен) и `403` (запись заблокирована).

**ADR-5. Подтверждение e-mail.** (a) ссылка с токеном, по `GET` сразу выдаёт ключ — почтовые сканеры (Outlook Safe Links и т. п.) открывают ссылку раньше человека и «съедают» ключ; (b) ссылка на экран интерфейса с токеном во фрагменте, ключ — по `POST` с кнопки — устойчиво к сканерам, токен не в журналах; (c) код из 6 цифр в письме — ввод вручную, нужен ещё лимит перебора кода. **Рекомендую (b).** Токен — 32 случайных байта, в базе SHA-256, одноразовый, 30 минут.

**ADR-6. Защита от массовой регистрации.** (a) лимиты: 5 запросов/ч с IP, 5 писем/сутки на адрес, `KEY_SIGNUP_GLOBAL_PER_DAY` (200) писем/сутки на сервер — бесплатно, без внешних сервисов, глобальный предел ещё и бережёт квоту и репутацию у почтового провайдера; (b) список одноразовых доменов — `KEY_EMAIL_BLOCKED_DOMAINS` в настройках (пусто), без внешнего списка: пополнять вручную по факту злоупотреблений; (c) капча (Cloudflare Turnstile, hCaptcha) — внешний сервис, скрипт третьей стороны на странице, передача IP и данных браузера третьей стороне — нужно упомянуть в тексте о данных, а для части пользователей это барьер. **Рекомендую (a)+(b) сейчас, (c) — только если увидим массовые регистрации**, отдельным решением владельца.

**ADR-7. Отправка писем.**

| Вариант | Цена (по моим знаниям, сверить) | Приватность | Доставляемость | Работа |
|---|---|---|---|---|
| (a) SMTP транзакционного провайдера из ЕС (Brevo — бесплатно ~300 писем/сутки; Mailjet — ~200/сутки) | 0 при наших объёмах | провайдер видит адреса и тексты писем, договор обработки данных (DPA), данные в ЕС | хорошая при SPF/DKIM на `solindex.net` | регистрация владельцем, записи DNS |
| (b) SMTP/API крупного облака (Amazon SES — ~0,1 $ за 1000 писем) | копейки, нужна карта и выход из «песочницы» | США, DPA есть | хорошая | аккаунт AWS, заявка на выход из песочницы |
| (c) свой почтовый сервер на VPS | 0 | данные не уходят третьим лицам | плохая: репутация IP хостинга, rDNS, у многих хостингов закрыт исходящий порт 25 `[не проверено для Contabo]` | постоянное сопровождение |
| (d) личный ящик владельца (Gmail и т. п. по паролю приложения) | 0 | смешивает личную почту с сервисом | средняя, суточные пределы | просто, но против условий почтовых сервисов для автоматических рассылок и раскрывает личный адрес |

Протокол в коде — SMTP (STARTTLS, порт 587) для любого варианта: провайдер меняется настройками, новой зависимости нет. **Рекомендую (a)**, с отправителем `noreply@solindex.net`, SPF и DKIM на домене. Выбор — владельцу (В1): внешний сервис, учётная запись на его имя, передача e-mail пользователей третьей стороне.

**ADR-8. Где экраны выдачи ключа.** (a) Sol Index (`frontend/`) — экраны «Get an API key», «Confirm», «My keys» на JSON-ручках, есть тесты и тёмная тема; (b) серверные HTML-формы, как `/developers` — без JS, но формы, CSRF и экранирование пишем сами, JSON-ручки всё равно нужны клиентам. **Рекомендую (a)**; `/developers` ссылается на экран.

**ADR-9. Счётчики использования.** (a) запись в базу на каждый запрос — лишняя нагрузка на каждый ответ; (b) агрегирование в памяти с выгрузкой раз в минуту — дёшево, потеря до минуты при падении; (c) журнал запросов — персональные данные и объём без нужды. **Рекомендую (b).**

## 6. Модель данных, миграция, поток

### Таблицы (миграция `0016_api_keys`)

`api_accounts` — учётные записи (ожидаемо сотни–тысячи строк):
- `id bigint generated always as identity` PK;
- `email text not null` — в нижнем регистре, `check (length(email) <= 254)`; `unique (email)`;
- `status text not null default 'active'`, `check (status in ('active','blocked'))`;
- `created_at timestamptz not null default now()`, `verified_at timestamptz null`, `blocked_at timestamptz null`, `block_reason text null` (`check length <= 500`), `note text null` (`check length <= 500`).
- Поиск admin по части e-mail — последовательным просмотром (`ILIKE`), при тысячах строк это доли миллисекунды; `pg_trgm` не нужен.

`api_keys`:
- `id bigint identity` PK; `account_id bigint not null references api_accounts(id) on delete cascade`;
- `key_hash bytea not null`, `check (octet_length(key_hash) = 32)`, `unique (key_hash)` — поиск ключа на каждый промах кэша;
- `prefix text not null` (11 символов) — индекс `ix_api_keys_prefix` для поиска admin;
- `created_at timestamptz not null default now()`, `last_used_at timestamptz null`, `revoked_at timestamptz null`, `revoke_reason text null`, `check (revoke_reason in ('owner','admin','replaced'))`;
- индекс `ix_api_keys_account_id (account_id)`.

`api_key_requests` — запросы подтверждения:
- `id bigint identity` PK; `email text not null`; `token_hash bytea not null unique`; `created_at`, `expires_at timestamptz not null`, `used_at timestamptz null`;
- индекс `(email, created_at)` — подсчёт запросов на адрес за сутки; удаляются через `KEY_REQUEST_RETENTION_HOURS` (24) после `expires_at` задачей очистки.

`api_key_usage_daily`:
- `account_id bigint references api_accounts(id) on delete cascade`, `key_id bigint references api_keys(id) on delete cascade`, `day date`, `requests bigint not null default 0`, `rejected bigint not null default 0` (ответы `429` этой записи); PK `(key_id, day)`; индекс `(account_id, day)` для сумм по записи;
- объём: действующие ключи × дни, при 1000 ключей и 90 днях — до 90 тыс. строк; старше `API_KEY_USAGE_RETENTION_DAYS` (90) удаляются.

`downgrade` удаляет четыре таблицы в обратном порядке; данных других таблиц миграция не трогает.

### Поток запроса

1. `RateLimitMiddleware`: если `API_KEYS_ENABLED`, `extract_api_key(scope)` берёт `X-Api-Key`, иначе `api_key` из строки запроса (первое значение); значение чужого формата в параметре (и в заголовке v1) — нет ключа.
2. Есть ключ → проверка счётчика неудачных попыток IP (`api_key_auth_limiter`) → `ApiKeyResolver.resolve(key)`: кэш → при промахе один запрос `SELECT k.id, k.account_id, k.revoked_at, a.status FROM api_keys k JOIN api_accounts a ... WHERE k.key_hash = :h` (по `unique`) через сессию API (действуют `DB_STATEMENT_TIMEOUT_SECONDS`; сбой базы → `503 service_busy`).
3. Ключ годен → `scope["mars.rate_identity"] = RateIdentity(kind="account", key="a:<account_id>", account_id, key_id)`, счётчик — `app.state.key_rate_limiter`; иначе — `RateIdentity(kind="ip", key=client_key(scope))` и `app.state.rate_limiter`. Неверный ключ → списать попытку с IP-лимитера и `api_key_auth_limiter`, ответить ошибкой своей версии.
4. `ResponseSizeMiddleware` и `HeavyQueryGate` берут личность из `scope["mars.rate_identity"]` (функция `rate_identity(scope)` с запасным `client_key`).
5. После ответа — `UsageCounter.add(account_id, key_id, rejected=status==429)` в памяти; задача `flush_api_key_usage` раз в 60 с — `INSERT ... ON CONFLICT (key_id, day) DO UPDATE SET requests = requests + excluded.requests` и `UPDATE api_keys SET last_used_at`. Задача `cleanup_api_keys` раз в сутки — просроченные запросы подтверждения и старые счётчики.

### Поток выдачи

`POST /keys/requests` → проверка формата и запрещённых доменов → лимит по IP (в памяти) → подсчёт запросов адреса за сутки в базе → глобальный дневной предел (в памяти, сброс в 00:00 UTC; после перезапуска — пересчёт по `api_key_requests` за сутки) → запись в `api_key_requests` → `Mailer.send(...)` в `to_thread` с таймаутом 10 с; ошибка SMTP → строка помечается удалённой, `503 mail_unavailable`. `POST /keys/confirm` в одной транзакции: `SELECT ... FOR UPDATE` запроса по `token_hash`, проверка `used_at`/`expires_at`, `INSERT ... ON CONFLICT (email) DO NOTHING` учётной записи, проверка статуса и лимита ключей, выпуск ключа, `used_at = now()`. Повтор и гонка двух подтверждений одним токеном — второй получает `400 invalid_token`.
