# Доработка: большие ответы v1 в лимите частоты

Редакция 2 (2026-11-21, HEAD `663175a`, миграции до `0015`; правки по ревью — AC-7, решение 5, «Готово, когда»). Основа: находка `security-reviewer` от 2026-11-21 (ответ v1 на весь сол без `page`); `docs/LEGACY-API.md` п. 5 и таблица расхождений; `docs/API.md`, «Ограничение частоты (v1 и v2)»; `docs/proposals/overload-protection.md` (раздел «Не входит»: «ответы v1 на весь сол — отдельной задачей»); код `app/api/ratelimit.py`, `app/core/ratelimit.py`, `app/main.py`, `app/core/errors.py`, `app/api/legacy/rovers.py`, `app/services/legacy.py`; один запрос к dev-базе `mars`.

## 0. Цель, границы, критерий

**Входит:**
- ответ на путях v1 стоит в лимите частоты столько запросов, сколько начатых `RATE_LIMIT_V1_BYTES_PER_REQUEST` (256 КиБ) байт ушло клиенту — после gzip; ответ до 256 КиБ по-прежнему стоит один запрос (вариант «а»);
- три строки лога в `app/core/errors.py` («Database error», «Unhandled error», «Database unavailable») — через `log_route(request)`, без сырого пути;
- тест: `/api/v2/rovers/Curiosity/photos` (регистр) при свободном и занятом шлюзе тяжёлых поисков ведёт себя как `/api/v2/rovers/curiosity/photos`.

**Не входит:** ограничение числа строк в ответе v1 без `page` (вариант «в», расхождение со старым API); серверный шлюз больших ответов v1 (вариант «б», см. ADR); счёт байтов в v2 (страницы v2 ограничены `per_page ≤ 100`, изображения конвертера сюда не относятся); защита от распределённой атаки со многих адресов.

**Готово, когда:** с одного IP без gzip запросы `GET /api/v1/rovers/curiosity/photos?sol=0` последовательно получают `200` не больше двух раз в минуту (параллельно — не больше `RATE_LIMIT_CONCURRENT`=4), дальше `429` с `Retry-After`, а запросы с других IP и обычные ответы v1 до 256 КиБ работают как раньше (AC-1…AC-12 зелёные, полный прогон зелёный).

## 1. Факты

1. Без `page` v1 отдаёт все снимки сола (`LEGACY-API.md` п. 5; `app/core/legacy_params.py:legacy_page_window` → `None`; `app/services/legacy.py:_list_photos`, `limit=None`).
2. Замер `security-reviewer`: curiosity sol 0 — 8 008 724 байт за 0,13–0,18 с работы цикла событий; с gzip — 138 КБ. При 60 запросах в минуту — ~8 МБ/с исходящего трафика с одного IP; три таких запроса одновременно поднимают медиану лёгких с 5 до 56 мс.
3. Dev-база `mars`, снимков на сол (все `sample_type`): Curiosity — максимум 4380, 99-й перцентиль 588, медиана 134, солов больше 1000 снимков — 3 из 4690; Perseverance — 3950 / 1239 / 237, больше 1000 — 35 из 1965; Spirit, Opportunity, Ingenuity — максимум 346–700. Снимок v1 весит ~1,8 КБ (вложенный `rover` со списком камер): обычный сол — ~250 КБ, худший — ~8 МБ.
4. Порядок прослоек (`app/main.py:147–176`, внешняя последней): `VaryAcceptEncoding` → `GZip` → `CORS` → `RateLimit` → `Caching` → приложение. Прослойка лимита видит тело до сжатия; чтобы считать байты «на проводе», счётчик должен стоять снаружи `GZip`.
5. `RateLimiter` (`app/core/ratelimit.py`) — корзины по ключу в каждом окне; `acquire` добавляет одно попадание, ожидание считает по переполнению суммы корзин — значит, переполнение на несколько единиц сразу корректно даёт `Retry-After` до выхода списанного из окна.
6. Шлюз тяжёлых поисков v2 (`app/core/overload.py`) v1 не касается; ключ клиента — `client_key(scope)` из `app/api/ratelimit.py`.
7. В `app/core/errors.py` три строки лога пишут `request.url.path` (`_handle_unexpected_error` — две, `_handle_db_error` — одна); остальные уже через `log_route`.

## 2. Критерии приёмки

Настройки в тестах, если не сказано иное: `RATE_LIMIT_PER_MINUTE=60`, `RATE_LIMIT_PER_HOUR=2000`, `RATE_LIMIT_V1_BYTES_PER_REQUEST` маленький (например, 1024), чтобы не набивать базу тысячами снимков.

| № | Критерий (вход → результат) | Кто проверяет | Слой теста |
|---|---|---|---|
| AC-1 | `RateLimiter.charge(key, n)` → добавляет `n` попаданий во все окна; после переполнения `acquire` возвращает `wait` до выхода списанного из окна; `charge` для нового ключа и `n ≤ 0` не падает (`n ≤ 0` — ничего) | qa-engineer | unit |
| AC-2 | Ответ v1 с телом `B` байт на проводе, `B > U` (`U` = `RATE_LIMIT_V1_BYTES_PER_REQUEST`) → после него в окнах списано `ceil(B / U)` запросов (1 при входе + `ceil(B/U) − 1` после); `X-RateLimit-Remaining` следующего ответа это показывает | qa-engineer | api |
| AC-3 | Ответ v1 с `B ≤ U`, а также `HEAD`, `304`, `4xx`/`503` с коротким телом → стоит ровно один запрос (как раньше) | qa-engineer | api |
| AC-4 | Тот же запрос с `Accept-Encoding: gzip` → списание по сжатым байтам (меньше, чем без gzip); байты считаются после сжатия | qa-engineer | api |
| AC-5 | Тело больше `U` на обоих префиксах v1 (`/api/v1/...`, `/mars-photos/api/v1/...`) → доплата по байтам; v2 (`/api/v2/...`) с телом больше `U` и пути без лимита (`/`, `/health`) — без доплаты | qa-engineer | api |
| AC-6 | Атака: с одного IP подряд запросы v1 без gzip с телом `≈ 10 × U` при лимите 30 в минуту → `200` получают первые 3, следующий — `429 {"errors": "Rate limit exceeded"}` с `Retry-After ≥ 1`; запрос с другого IP в это время → `200` | qa-engineer | api |
| AC-7 | Клиент оборвал соединение посреди тела (ошибка `send`) → списано по байтам, переданным серверу (включая сообщение, на котором `send` упал), исключение не теряется и не подменяется, счётчик одновременных запросов освобождён | qa-engineer | unit (ASGI) |
| AC-8 | `RATE_LIMIT_ENABLED=false` → доплаты нет, заголовков нет; `RATE_LIMIT_V1_BYTES_PER_REQUEST < 1024` → ошибка настроек при старте | qa-engineer | unit |
| AC-9 | Список v1 (`sol=N` без `page`) на занятом шлюзе тяжёлых поисков v2 → `200` (v1 шлюз по-прежнему не проходит) | qa-engineer | api |
| AC-10 | Логи «Database error», «Unhandled error», «Database unavailable» содержат шаблон маршрута (`/rovers/{rover}/photos`), а не путь запроса: запрос `/api/v1/rovers/zzsecretzz/photos?sol=1` с ошибкой базы → в записи лога нет `zzsecretzz` | qa-engineer | api |
| AC-11 | `/api/v2/rovers/Curiosity/photos` с тяжёлым фильтром: шлюз свободен → `200`, тело совпадает с `/curiosity/`; шлюз полон → `503 service_busy` (обойти шлюз регистром нельзя); лёгкий фильтр (`sol=1`) при полном шлюзе → `200` | qa-engineer | api |
| AC-12 | Прогон существующих тестов лимита → они (`X-RateLimit-*`, одновременные запросы, admin) зелёные без правок, кроме явно связанных с новой настройкой | qa-engineer | все |

## 3. Решения

1. **Считать байты, а не строки.** Байты — то, что на самом деле расходует канал; строки дают неравную цену для v1 c разным весом снимка и наказывают клиентов с gzip.
2. **Байты после gzip.** Честный клиент с `Accept-Encoding: gzip` (браузеры, `requests`, `curl --compressed`) за весь сол Curiosity платит один запрос; без сжатия — 31. Злоумышленнику без gzip это и нужно ограничить.
3. **Только v1.** В v2 страницы ограничены (`per_page ≤ 100`); изображения конвертера и Sol Index не должны получать новую цену без отдельного решения.
4. **Списание после отправки.** Размер известен только по факту; заголовки `X-RateLimit-*` самого большого ответа доплату ещё не учитывают, следующие — учитывают. Предварительной проверки «хватит ли бюджета» нет: последний большой ответ в окне всегда проходит, после него — `429`.
5. **Единица — 256 КиБ.** Обычный сол v1 (~250 КБ) — один запрос; худший сол без gzip (8 МБ) — 31. С одного IP: ~2 таких ответа в минуту → ~270 КБ/с вместо ~8 МБ/с, в часовом окне (2000) — ~64 в час (~140 КБ/с в среднем). Параллельно (до `RATE_LIMIT_CONCURRENT`=4 запросов) один IP успевает получить до 4 больших ответов до первой доплаты — ~530 КБ/с в первую минуту; часовой предел тот же. Принято как допустимое (ревью безопасности, MEDIUM-1): контракт обещает только, что последний большой ответ в окне проходит.
6. `LEGACY-API.md` п. 5 («без `page` — все фото») **не меняется**: ответ остаётся полным, меняется только его цена в лимите — новая строка в таблице расхождений.

## 4. Текст для контрактов (нужно «ок» владельца)

**`docs/API.md`, «Ограничение частоты (v1 и v2)»**, новый пункт после «Одновременные запросы»:

> - **Размер ответов v1.** Ответ на путях v1 (`/api/v1/*`, `/mars-photos/api/v1/*`) стоит в обоих окнах столько запросов, сколько начатых `RATE_LIMIT_V1_BYTES_PER_REQUEST` (по умолчанию 262 144 байта, 256 КиБ) в его теле в том виде, в каком оно ушло клиенту (после сжатия gzip), но не меньше одного. Ответы v2 стоят по одному запросу независимо от размера.

## 5. ADR

| Вариант | Плюсы | Минусы |
|---|---|---|
| **(а) байты на проводе в лимите частоты (рекомендую)** | режет именно трафик с одного IP (~30 раз для худшего сола без gzip); не трогает форму ответа; честные клиенты с gzip и обычные солы не замечают; общая прослойка, без правок сервисов | доплата — после ответа (последний большой в окне проходит); меняет текст раздела лимита |
| (б) серверный шлюз больших ответов v1 (> N строк, 503 «Server is busy») | ограничивает одновременную нагрузку на цикл событий со многих IP | не ограничивает трафик: один поток на быстрый клиент всё равно забивает канал; честный клиент получает `503` из-за чужих загрузок; держать место нужно до конца отправки (своя обёртка ответа) |
| (в) потолок строк без `page` | проще всего, жёсткая граница размера | ломает старых клиентов, которые берут сол целиком — нарушение п. 5 `LEGACY-API.md`, главного обещания «переезд сменой хоста» |

Остаточный риск после (а): распределённая атака со многих IP — как и для любого другого лимита на IP; при необходимости (б) добавляется позже поверх (а).

## 6. Модель данных, миграция, поток

Миграций нет. Поток: запрос → `VaryAcceptEncoding` → **`ResponseSizeMiddleware`** (новая, снаружи `GZip`) → `GZip` → `CORS` → `RateLimit` (как раньше: `enter`, `acquire` — 1 запрос) → приложение. `ResponseSizeMiddleware` для путей v1 при включённом лимитере оборачивает `send`, суммирует длину `body` сообщений `http.response.body`; в `finally` (и при обрыве) вызывает `limiter.charge(client_key(scope), ceil(B / U) − 1)`. Для остальных путей — прозрачна.

## 7. Задания ролям и общие имена

**Общие имена:**
- `Settings.rate_limit_v1_bytes_per_request: int = 262_144` (env `RATE_LIMIT_V1_BYTES_PER_REQUEST`, ≥ 1024);
- `RateLimiter.charge(key: str, hits: int) -> None` в `app/core/ratelimit.py`;
- `ResponseSizeMiddleware` в `app/api/ratelimit.py`; читает `app.state.rate_limiter` и `app.state.v1_bytes_per_request` (или настройку) на каждый запрос, как `RateLimitMiddleware`;
- `extra_hits(body_bytes: int, unit: int) -> int` — `max(0, ceil(body_bytes / unit) − 1)`, в `app/api/ratelimit.py`;
- `is_legacy_path` из `app/core/errors.py` — определение путей v1.

- `backend-dev`: `RateLimiter.charge`; `ResponseSizeMiddleware` и `extra_hits`; настройка в `Settings` и `.env.example`; подключение в `app/main.py` снаружи `GZip` (только если лимит включён); три строки лога в `app/core/errors.py` → `log_route(request)`.
- `qa-engineer`: AC-1…AC-12 и таблица «AC → тест»; граничные: тело ровно `U`, `U + 1`, пустое тело, несколько сообщений тела (`more_body`), исключение в `send`.
- `tech-writer`: не нужен сейчас — README и `/developers` лимит в байтах не описывают `[проверить в ревью]`; если описывают — правка по тексту раздела 4.
- `data-engineer`: не нужен — объёмы взяты из замера `security-reviewer` и одного запроса к dev-базе (раздел 1, п. 3).
