# Автослияние и автовыкладка (CI/CD) — спецификация для devops

Редакция 1 (2026-11-26, HEAD `9b0371f`). Основа: решение владельца 2026-11-26 (ветка на этап → PR → зелёный CI → автослияние → автовыкладка на VPS), `deploy/README.md` (VPS, `update.sh`, откат), `.github/workflows/ci.yml` (задачи `Lint, migrations, tests`, `Frontend`, `Docker build`), защита `master` (запрет force-push и удаления, правила действуют и для администратора).

## 0. Цель, границы, критерий

**Входит:** обязательные проверки CI для слияния в `master`; автослияние PR из веток `stage-*`, `fix-*`, `process/*` при зелёном CI; автоматическая выкладка на VPS после слияния с бэкапом, проверкой и автооткатом; защита от опасных миграций меткой `needs-owner`; уведомления в Telegram.
**Не входит:** слияние PR с меткой `needs-owner` без «ок» владельца; выкладка на ноутбук (запасной вариант остаётся ручным); смена хостинга; подпись коммитов.
**Готово, когда:** тестовый PR с безобидной правкой проходит путь «ветка → CI → автослияние → выкладка → `smoke.py`» без участия человека, а PR с миграцией `drop_column` остаётся неслитым до «ок».

## 1. Факты
- CI (`ci.yml`) запускается на `push` в `master` и на `pull_request`; задачи: `Lint, migrations, tests` (ruff, миграции на пустой базе, `alembic check`, `pytest -n 4`), `Frontend` (lint, typecheck, test, build), `Docker build`.
- Защита `master` сейчас: запрещены force-push и удаление, `enforce_admins=true`, обязательных проверок и PR нет.
- На VPS выкладка — `/srv/mars/repo/deploy/vps/update.sh`: pull, сборка образа `mars-rover-api:<commit>`, бэкап, миграции, пересоздание `app`, проверка `/health`, удаление старых образов. Он ничего не откатывает сам (README, «Update and rollback»). Откат приложения: `APP_TAG=прошлый_тег` в `.env` и `docker compose up -d app`.
- Вход на VPS: пользователь `deploy`, только по ключу, порт 22 открыт, `fail2ban` включён. `deploy` — в группе `docker` и с `sudo` без пароля (доверие ключу).
- Бот Telegram и `notify` в `lib.sh` уже есть.

## 2. Критерии приёмки

| № | Критерий (вход → результат) | Кто проверяет | Слой |
|---|---|---|---|
| AC-1 | PR в `master` с красной задачей CI → кнопка слияния недоступна, автослияние не включается | devops | настройки репозитория |
| AC-2 | PR из ветки `stage-*` без метки `needs-owner`, все три задачи CI зелёные → PR сливается сам (squash), ветка удаляется | devops | workflow |
| AC-3 | PR с меткой `needs-owner` и зелёным CI → не сливается, пока владелец не снимет метку или не вмешается | devops | workflow |
| AC-4 | PR добавляет миграцию с `drop_column`, `drop_table` или переименованием → задача `migration-guard` ставит метку `needs-owner` и пишет комментарий с причиной | devops | CI |
| AC-5 | PR меняет `docs/API.md` или `docs/LEGACY-API.md` → то же, метка `needs-owner` | devops | CI |
| AC-6 | Слияние в `master` → выкладка на VPS стартует сама, одна за раз (очередь по `concurrency`), результат в Telegram | devops | workflow |
| AC-7 | Выкладка: перед миграциями делается бэкап; после перезапуска `smoke.py https://api.solindex.net` проходит 15/15 → задача зелёная, сообщение «выложено: <commit>» | devops | workflow |
| AC-8 | После выкладки `smoke.py` или `/health` падает → приложение автоматически откатывается на прошлый тег, в Telegram «откат: <commit>, причина»; задача красная | devops | скрипт на сервере |
| AC-9 | Вход с ключом выкладки и командой, отличной от разрешённой, или запрос оболочки → отказ: ключ в `authorized_keys` ограничен принудительной командой (`command="…/deploy-entry.sh"`, `restrict`) | devops, security-reviewer | сервер |
| AC-10 | Выкладка отработала → в логах задач нет приватного ключа и значений секретов (маскируются), они лежат только в секретах GitHub | security-reviewer | workflow |
| AC-11 | Прямой пуш в `master` → отклонён (нужен PR); пуш в `stage-*` → принят | devops | защита ветки |

## 3. Решения (рекомендации)
1. **Вход на сервер из GitHub Actions** — отдельный ключ только для выкладки, в `authorized_keys` с `command="/srv/mars/repo/deploy/vps/deploy-entry.sh",restrict`. Скрипт принимает один аргумент (SHA коммита), проверяет, что он в `origin/master`, и запускает `update.sh` с автооткатом. Отпечаток сервера хранится в секрете (`KNOWN_HOSTS`), `StrictHostKeyChecking=yes`. Альтернатива (self-hosted runner на VPS) отвергнута: на проде появился бы процесс с доступом к GitHub.
2. **Откат** — обёртка над `update.sh`: запомнить текущий `APP_TAG`; после выкладки подождать `/health` и выполнить `smoke.py` на `http://127.0.0.1:8000`; при неудаче вернуть `APP_TAG`, `docker compose up -d app`, уведомить. Откат не трогает базу: миграции в PR должны быть обратно совместимыми (расширение, потом сужение отдельным PR).
3. **Миграции** — `migration-guard` читает новые файлы в `migrations/versions/` и ищет `drop_`, `rename`, `alter_column(... type_` / `nullable=False` на непустой таблице; найдено — метка `needs-owner`. Добавляющие миграции (новая колонка, индекс) проходят автоматически.
4. **Автослияние** — настройка репозитория «Allow auto-merge» и вызов `gh pr merge --auto --squash` из `/stage` или workflow `automerge.yml` для PR из веток `stage-*`, `fix-*`, `process/*` без метки `needs-owner`. Обязательные проверки в защите `master`: `Lint, migrations, tests`, `Frontend`, `Docker build`, `migration-guard`.
5. **Контроль контракта** (отдельным шагом после запуска базового конвейера): `oasdiff` и `schemathesis` как проверки CI.
6. **Подпись коммитов** — не включаем.

## 6. Задания ролям
- `devops`: `.github/workflows/deploy.yml` (триггер: `push` в `master`, `concurrency: deploy-prod`, шаги: `ssh` с принудительной командой, `smoke.py` снаружи, уведомление); `.github/workflows/automerge.yml` и `migration-guard` (скрипт в `.github/scripts/migration_guard.py` с тестами в `tests/unit/`, их пишет `qa-engineer`); `deploy/vps/deploy-entry.sh` и автооткат; правки `deploy/README.md`; настройка защиты `master` и «Allow auto-merge» (после «ок» владельца: права репозитория).
- `qa-engineer`: тесты `migration_guard.py` по AC-4 и AC-5 (в `tests/unit/`).
- `security-reviewer`: AC-9, AC-10 до включения.
- Владелец (один раз): создать пару ключей для выкладки (приватный — в секрет GitHub `DEPLOY_SSH_KEY`, публичный — в `authorized_keys` на VPS с ограничениями), добавить секреты `DEPLOY_HOST` и `KNOWN_HOSTS`; включить «Allow auto-merge»; разрешить пуши в ветки этапов в `.claude/settings.json` (сделано владельцем).

## 7. Проверка и бюджет
- `uv run ruff check .`, `uv run pytest -q -n 12`; проверка на тестовом PR (безобидная правка README) и на PR с миграцией `drop_column` (AC-4) в отдельной ветке, не сливаемой.
- Ревью: `reviewer`, `security-reviewer` (публичная поверхность: образ, развёртывание, доступ на сервер).
- Расход: `devops` порядка 1 запуска, `qa-engineer` небольшой, `security-reviewer` один.

## 8. Внешние запросы
Нет запросов к внешним сайтам, кроме GitHub и собственного VPS (SSH и `smoke.py` по своему адресу).

## 9. Вопросы владельцу
1. **Откат при красном `smoke.py`:** автоматически (рекомендую) или только уведомление?
2. **Выкладка при каждом слиянии или по расписанию** (например, ночью)? Рекомендую при каждом слиянии: ночью проблему найти дольше.
3. **Нужна ли пауза** (кнопка «отложить выкладку»), например переменная `DEPLOY_PAUSED` в настройках репозитория? Рекомендую да.
