# Доработка: защита API от перегрузки тяжёлыми запросами — черновик архитектора

Редакция 1 (2026-11-21, HEAD `3f3c02f`, миграции до `0014`). Основа: `docs/reports/stage-18b-fields.md` §8 (подразделы «Холодный кэш и покрывающий индекс», «Тяжёлый запрос без `near`»), находки `security-reviewer` этапа 18B-3; `docs/API.md` (таблица ошибок, «Одновременные запросы», «Перегрузка»); `docs/LEGACY-API.md` (строки расхождений 137–138); код `app/db/session.py`, `app/main.py`, `app/core/config.py`, `app/core/errors.py`, `app/api/ratelimit.py`, `app/services/v2.py` (`_total`, `_sol_range_total`, `search_photos`, `_photo_page`), `app/repositories/photos.py`; `deploy/laptop/compose.yml`; один `EXPLAIN` на dev-базе `mars`.

## 0. Цель, границы, критерий

**Входит:**
- серверный «шлюз тяжёлых запросов»: не больше `HEAVY_QUERY_CONCURRENCY` (по умолчанию 2) тяжёлых поисков v2 одновременно на весь сервер, лишний сразу получает `503 service_busy` с `Retry-After`, не занимая соединение надолго;
- классификация «тяжёлый» без обращения к базе — по форме фильтра, той же функцией, что выбирает способ подсчёта `total`;
- явные `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` в `Settings` (сейчас неявные 5 + 10) и `jit=off` для всех соединений API;
- `total` для `sample_type=full` без сола и без других фильтров — из `sol_summaries` (сейчас — подсчёт по таблице);
- по замеру `data-engineer`: расширить `ix_photos_near_cover` столбцами `sample_type`, `camera_id`, чтобы `count` по стоянкам и `near` с этими фильтрами шли index-only.

**Не входит:** ограничение или приближённый `total` (смена контракта — вопрос 10.3, рекомендую не делать сейчас); отмена запроса в базе при обрыве клиента; разные `statement_timeout` для лёгких и тяжёлых запросов; лимит тяжёлых запросов на IP; индексы под все сочетания фильтров (их слишком много, поэтому и нужен шлюз); изменения v1 (там тяжёлых запросов нет, см. 1.6).

**Готово, когда:** при непрерывной нагрузке тяжёлыми поисками с нескольких IP лёгкие запросы v1 и v2 отвечают `200` без `503`, а сверх лимита тяжёлые получают `503 service_busy` сразу (AC-1…AC-12 зелёные, живой прогон AC-13 записан в отчёт).

## 1. Факты

1. Пул API — умолчания SQLAlchemy: `pool_size=5`, `max_overflow=10` (15 соединений); задан только `pool_timeout` = `DB_POOL_TIMEOUT_SECONDS` = 5 с (`app/db/session.py:44-47`, `app/main.py:68-73`). Соединение берётся при первом запросе к базе и держится до конца запроса (сессия на запрос, `get_session`).
2. На каждое соединение API: `statement_timeout` 5 с и `max_parallel_workers_per_gather=0`; `jit` не выключен, `SET LOCAL jit = off` есть только у `near` (`app/repositories/photos.py:405-417`). JIT добавляет 160-210 мс любому плану дороже 100 000 (отчёт 18B §8, «Ловушки», п. 1).
3. Лимит на IP: 60/мин, 2000/ч, одновременно `RATE_LIMIT_CONCURRENT=4` (IPv6 по /64), лишний — `429` (`app/core/config.py:117-121`, `docs/API.md` «Одновременные запросы»). Четыре-пять IP по 4 запроса держат все 15 соединений; остальные ждут 5 с и получают `503 service_busy`.
4. `503 service_busy` сейчас бывает по двум причинам: `PoolTimeoutError` и SQLSTATE 57014/53xxx (`app/core/errors.py:298-307`, `_handle_db_error`), с `Retry-After: 5` и `Cache-Control: no-store`.
5. Запрос держит соединение дольше 5 с: `total` и ключи страницы — отдельные операторы (`_photo_page`, `search_photos`), у каждого свой `statement_timeout`.
6. v1 тяжёлых запросов не делает: без `sol` и `earth_date` отвечает пустым списком (`LEGACY-API.md` п. 1), иначе выборка одного сола или дня по индексу; `latest_photos` и манифест — по `sol_summaries`. v1 страдает только как «соседи» по пулу.
7. Замер (dev-база, 1,73 млн снимков, куча 4,2 ГБ, `jit=off`, без параллельных воркеров): `count(*) … rover_id='curiosity' AND sample_type='full' AND site BETWEEN 0 AND 100000` — отмена по 8 с (отчёт 18B: тёплый 2,78 с, Seq Scan 538 тыс. страниц, оценка 310 741 строк против 139 062). Тот же `count` без `site` — 339 мс, Index Only Scan по `ix_photos_full_rover_id_sol_camera_id_id`, `Heap Fetches: 0`.
8. Индексы `photos` сейчас: `ix_photos_near_cover (rover_id, site, drive) INCLUDE (sol, taken_at, id) WHERE site IS NOT NULL` (79 МБ), отдельного индекса по `site` нет; `ix_photos_rover_id_sample_type_sol` (176 МБ); частичный `ix_photos_full_rover_id_sol_camera_id_id` (75 МБ).
9. `near` с фильтрами вне индекса (`sample_type`, камера, даты, `meta`) на весь район — до 5 с на холодном кэше (отчёт 18B, «Холодный кэш», строка `keys P r=50 + sample_type=full`: 4974 мс).
10. `_total` (`app/services/v2.py:733-758`) уже решает, откуда брать `total`: из `sol_summaries` / `camera_sol_counts` или `count_photos`. Для `sample_type=full` без сола, диапазона и камеры он идёт в `count_photos`, хотя `sol_range_total_photos(…, None, None, full_only=True)` отвечает тем же из сводок.
11. Продакшен: один процесс uvicorn (`deploy/README.md`, Dockerfile), поэтому семафор в памяти процесса — серверный. Postgres 16 в Docker без лимитов CPU и памяти (`deploy/laptop/compose.yml`), `max_connections=100`, `shared_buffers=128MB` (по умолчанию). Docker на машине разработки видит 16 CPU, 16 ГБ; на ноутбуке-продакшене `[не проверено]`, это задача `devops`.
12. `[не проверено]` Насколько тяжелы «лёгкие» по классификации сочетания на холодном кэше (`earth_date` + `meta`, `sol` + `near`, только `site_min/site_max`) — задача `data-engineer` (AC-13, AC-14).

## 3. Решения

1. **Шлюз тяжёлых запросов** — `asyncio.Semaphore` в памяти процесса (приложение — один процесс), без очереди: занято — сразу `503 service_busy`, `Retry-After: 5`. Почему: отказ ничего не стоит базе, лёгкие запросы гарантированно получают ≥ `pool − H` соединений (ADR-1, ADR-2).
2. **Тяжёлое определяется по форме фильтра, не по времени.** Одна чистая функция `classify_total(flt) -> TotalSource` возвращает источник `total`; `_total` выбирает по ней ветку, шлюз — по ней же класс. Тяжёлый = `scan_heavy` хотя бы у одного фильтра запроса. Так классификация не расходится с тем, что реально выполнится (ADR-2).
3. **Где берётся слот** — в сервисе v2 после проверки параметров и разрешения камер (лёгкие запросы), до первого подсчёта по `photos`; держится до конца загрузки страницы. Ожидания нет, поэтому соединение, уже взятое на лёгкую часть, не простаивает.
4. **Пул явно**: `DB_POOL_SIZE=10`, `DB_MAX_OVERFLOW=5` (итого 15 — как сейчас, поведение не меняется), `HEAVY_QUERY_CONCURRENCY=2`; лёгким остаётся ≥ 13 соединений. `jit=off` для всех соединений API (в `server_settings` рядом с `statement_timeout`); `SET LOCAL jit = off` у `near` становится лишним, его можно убрать.
5. **Индекс** — по замеру AC-15: пересоздать `ix_photos_near_cover` как `(rover_id, site, drive) INCLUDE (sol, taken_at, id, sample_type, camera_id) WHERE site IS NOT NULL`. Это сокращает время, на которое тяжёлый запрос держит слот, в самых частых тяжёлых случаях (стоянки/`near` + `sample_type`/камера), но не заменяет шлюз (ADR-3).
6. **`total` не меняется**: точное число, как в контракте (ADR-4, вопрос 10.3).
7. **v1 шлюз не проходит** (факт 1.6); выигрывает от него как сосед по пулу. `LEGACY-API.md` не меняется.

## 5. ADR

**ADR-1. Чем ограничивать: шлюз только для тяжёлых, общий лимит на все запросы к базе, или только пул.**
- (а) Только явный пул (крупнее/меньше). Плюсы: одна настройка. Минусы: не разделяет классы — пять атакующих IP с тяжёлыми запросами по-прежнему занимают все соединения, лёгкие ждут 5 с и получают `503`. Не решает находку 2.
- (б) Общий семафор на все запросы API к базе с немедленным отказом. Плюсы: просто, без классификации. Минусы: то же, что (а) — тяжёлые выедают общие места, отказ получают и лёгкие; по сути дублирует пул.
- (в) Отдельный шлюз для тяжёлых (H мест) + общий пул. Плюсы: тяжёлых одновременно ≤ H, лёгким гарантированно ≥ пул − H соединений; отказ мгновенный и дешёвый. Минусы: нужна классификация; при атаке честные тяжёлые поиски получают `503` (лёгкие — нет).
- **Рекомендация: (в).** Это единственный вариант, при котором лёгкие запросы (большая часть трафика, весь v1 и Sol Index по солу) не страдают от тяжёлых.

**ADR-2. Как классифицировать «тяжёлый» до похода в базу.**
- (а) По пути (весь `/api/v2/photos` — тяжёлый). Просто, но грубо: мультировер по солу или без фильтров дешёвый, а `/rovers/{r}/photos` с тяжёлыми фильтрами пропускается.
- (б) По оценке планировщика (`EXPLAIN` перед запросом). Точнее, но лишний запрос к базе на каждый поиск, оценки уже ошибаются в 2 раза (факт 1.7) и требуют соединения — того, что мы бережём.
- (в) По времени выполнения (адаптивно, «был медленным — тяжёлый»). Нужна память по формам запросов, первая атака проходит.
- (г) По форме фильтра той же функцией, что выбирает источник `total` (`classify_total`). Плюсы: чистая функция, без базы, тестируется таблицей; не расходится с выполнением; консервативна — всё, что считается по куче без закрепления сола/даты, тяжёлое. Минусы: при новых фильтрах её надо дополнять (тест AC-1 таблицей это ловит), часть «лёгких» сочетаний надо подтвердить замером (AC-14).
- **Рекомендация: (г).**

**ADR-3. Чинить ли подсчёт индексами.**
- (а) Индекс под каждое тяжёлое сочетание. Сочетаний десятки (даты × `sample_type` × камера × `meta` × стоянки × `near`), каждый индекс 30-180 МБ на таблице 4,2 ГБ, замедляет синхронизацию. Нет.
- (б) Один индекс на самый частый случай: расширить `ix_photos_near_cover` столбцами `sample_type`, `camera_id` в `INCLUDE` (оценка +15-25 МБ к 79 МБ). Покрывает находку 1 (`site_*` + `sample_type`) и основной случай находки 3 (`near` + `sample_type`/камера), даты и `meta` — нет. Миграция: `CREATE INDEX CONCURRENTLY` нового, `DROP INDEX CONCURRENTLY` старого, обратимо.
- (в) Ничего, только шлюз.
- **Рекомендация: (б), но только если AC-15 подтвердит план и время на dev-базе;** иначе (в). Шлюз нужен в любом случае.

**ADR-4. Ограничивать или приближать `total`.**
- (а) Точный `total` (как сейчас). Контракт не меняется; дорогие подсчёты остаются, но ограничены шлюзом и `statement_timeout`.
- (б) Потолок: считать до N (например, `LIMIT 10001` в подзапросе) и отдавать `total = 10000` + признак `total_capped: true`. Подсчёт дешевле в разы при больших выборках; меняет контракт (новое поле, смысл `total`), фронтенду нужен показ «10 000+».
- (в) Оценка планировщика (`reltuples`/`EXPLAIN`) — неточно в 2 раза (факт 1.7), смена контракта.
- **Рекомендация: (а) сейчас;** (б) — отдельной доработкой, если после выкладки в логах будет заметна доля `503` у честных тяжёлых поисков. Решает владелец (вопрос 10.3).

**ADR-5. Ждать ли места в шлюзе.**
- (а) Не ждать — сразу `503`. Атакующему отказ ничего не стоит, но и серверу; соединение не простаивает.
- (б) Ждать до 1-2 с. Меньше ложных отказов при случайном совпадении двух честных поисков; ожидающий держит соединение, уже взятое на лёгкую часть запроса (марсоход, камеры), — при атаке это снова съедает пул.
- **Рекомендация: (а).** После 3.2 и 3.5 в тяжёлые попадает узкий круг поисков, совпадения честных редки; `Retry-After` клиенту понятен.

## 6. Модель данных, миграция, поток

**Классы источника `total`** (`TotalSource`, порядок проверки сверху вниз; «закреплён» = задан `sol` или `earth_date`):

| Фильтр (кроме `rover`, страницы, сортировки) | Класс | Источник `total` |
|---|---|---|
| ничего; диапазон солов; камера; камера + `full`; `sample_type=full` (+ диапазон солов) | `summary` | `sol_summaries` / `camera_sol_counts` (`full` без диапазона — новое, решение 0) |
| `sol` (с любыми другими фильтрами); `earth_date` (с любыми другими) | `summary` или `scan_light` | как сейчас: сводка по солу или подсчёт по индексу сола/дня |
| только стоянки (`site`, `site_min`/`site_max`, `drive_*`), только `near` (+ диапазон солов) | `scan_light` | `count_photos`, index-only по `ix_photos_near_cover` |
| не закреплён и есть любое из: `date_min`/`date_max`, `local_time_*`/`golden_hour`, `min_width`/`min_height`, `sample_type` ≠ `full`; или стоянки/`near` вместе с `sample_type`, камерой, датами, `meta` | `scan_heavy` | `count_photos` по куче |

Граница `scan_light`/`scan_heavy` для стоянок + `sample_type`/камера сдвигается в `scan_light`, только если принят индекс 3.5 и AC-15 зелёный; до тех пор — `scan_heavy`.

**Решение 2026-11-21 (после AC-14/AC-15, «ок» владельца на индекс):** индекс 3.5 делаем (AC-15: подсчёт находки 1 — 2426 → 81 мс холодный, Index Only Scan, Heap Fetches 0; +23 МБ). Стоянки/`near` + `sample_type` (без камеры, дат, `meta`) — `scan_light`. Стоянки/`near` + камера — остаются `scan_heavy` (замера с камерой не было). Все строки `scan_light` из AC-14 — холодные ≤ 178 мс, переносов нет. Предикат действующего `ix_photos_near_cover` — `WHERE site IS NOT NULL` (миграция 0014), новый — такой же. Уточнение: «стоянки/`near` + `sample_type`» — любое значение `sample_type` (индекс отвечает на любое), то есть строка «`sample_type` ≠ `full` — тяжёлый» таблицы выше относится к поискам без стоянок и `near`. Пример тяжёлого запроса находки 1 после индекса стал лёгким; в AC-3 тяжёлый запрос — `/rovers/curiosity/photos?date_min=2012-08-06&sample_type=full`.

**Миграция `0015`** (только при решении 3.5): `upgrade` — `CREATE INDEX CONCURRENTLY ix_photos_near_cover_swap ON photos (rover_id, site, drive) INCLUDE (sol, taken_at, id, sample_type, camera_id) WHERE site IS NOT NULL`, `DROP INDEX CONCURRENTLY ix_photos_near_cover`, переименование в `ix_photos_near_cover`; в `autocommit_block()` (как `0014`). `downgrade` — обратно к `INCLUDE (sol, taken_at, id)`. После миграции на проде — `VACUUM (ANALYZE, PARALLEL 0) photos` (карта видимости для index-only, см. отчёт 18B), шаг в runbook. Таблиц и столбцов не добавляется.

**Поток запроса v2-поиска:** роутер → сервис: проверка параметров (`422`) → марсоход (`404`) → камеры → фильтры → `classify_total` для каждого фильтра → если есть `scan_heavy`: `async with gate.slot()` (занято → `ServiceBusy`, `503`) → `_total` → ключи страницы → строки → ответ; слот освобождается в `finally`. Синхронизация, загрузки, admin и v1 шлюз не проходят. Внешних запросов нет.
