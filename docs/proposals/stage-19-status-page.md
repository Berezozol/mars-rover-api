## 0. Цель, границы, критерий

**Входит:**
- страница `/status` в Sol Index: по каждому марсоходу с синхронизацией — последняя успешная синхронизация, дата самого свежего снимка, флаги «синхронизация отстаёт» и «снимки отстают» и общий статус;
- ссылка «Status» в подвале всех страниц.

**Не входит:**
- изменения API и `/health/sync`;
- история аптайма и запросы к сторонним сервисам из браузера;
- архивные марсоходы (Spirit, Opportunity, Ingenuity): они не синхронизируются, о них — одна строка.

**Готово, когда:** `/status` показывает данные `/health/sync` во всех трёх состояниях (`ok`, `stale`, `degraded`) и проходит `/ui-check`.

## 2. Критерии приёмки

| № | Критерий (вход → результат) | Кто проверяет | Слой теста |

## 3. Решения

1. Запрос идёт к `/health/sync` напрямую: тот же origin, без лимита частоты, `no-store`. Тело приходит и при `503`, поэтому клиент читает JSON при любом коде ответа.
2. Пороги (24 ч, 21 день) зашиты в тексты как в контракте. Если их поменяют в настройках сервера, тексты разойдутся с реальными порогами. Это приемлемо, потому что флаги считает сервер.
3. Без внешних виджетов: UptimeRobot у нас только для оповещений. Его публичная страница, если владелец её заведёт, — просто ссылка (вопрос 1).

## 7. Задания ролям и общие имена

**Общие имена:**
- маршрут `{ name: "status" }` в `matchRoute`;
- страница `frontend/src/pages/Status.tsx`;
- клиент `api.healthSync()` возвращает `{status, rovers?, db?}` при любом HTTP-коде с телом JSON;
- `data-testid`: `status-overall`, `status-rover-<slug>`, `status-sync-late`, `status-photos-late`, `status-refresh`, `status-checked-at`, `footer-status-link`.

**Роли:**
- `frontend-dev` — реализация в `frontend/` (кроме тестов), стили — токены `styles-base.css`, без нового макета.
- `frontend-qa` — `frontend/tests/status.test.tsx` по AC-1–AC-8.
