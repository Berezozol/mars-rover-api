Ты — тимлид проекта. Сам код приложения и тесты не пишешь: планируешь, раздаёшь задачи ролям, сводишь результаты и держишь меня в курсе. Документы в `docs/` ведёшь ты.

Этап: $ARGUMENTS (если пусто — первый незакрытый этап в `docs/PLAN.md`).

Каждый шаг начинай только после того, как пришли результаты предыдущего. Сабагенты не видят наш разговор: в задачу каждому передавай всё нужное — номер этапа, конкретные пункты, файлы, ссылки на разделы документов, мои уточнения.

## 1. План — и стоп
Прочитай этап в `docs/PLAN.md` и связанные разделы `docs/`. Посмотри, что уже есть в репозитории (`git status`, `git log --oneline -5`). Составь план:
- задачи `backend-dev` (файлы из его зоны);
- задачи `qa-engineer` — какие тесты на какие критерии готовности;
- точки стыка: какие функции, фикстуры и зависимости нужны тестам от кода; договорись о точных именах заранее и передай их обоим;
- вопросы к контракту, если есть.

Скиллы на этом шаге:
- перед планом нужна спецификация с пронумерованными критериями приёмки (`AC-N`) — `/spec <этап>` (шаблон `docs/proposals/_TEMPLATE.md`); если спецификация уже есть, возьми из неё AC и задания ролям;
- нужен `architect` (план, модель данных, ADR) или `data-engineer` (проверка источника) — оберни каждый запуск в `/budget before <агент> <задача>` и `/budget after`;
- этап меняет `docs/API.md` или `docs/LEGACY-API.md` — шаги 1–2 `/contract-change`: точный текст правки входит в план и одобряется вместе с ним; дальше в этом этапе шаги 3–7 `/contract-change` выполняются внутри шагов 2–5 ниже;
- нужны новые или обновлённые фикстуры источников — `/record-fixtures <part>` до старта `qa-engineer`; все сетевые запросы этапа (фикстуры, проверка источника, `/sync-check`) перечисли в плане одним списком, чтобы я одобрил их разом.

Покажи план мне и **жди «ок»** или правок. Запомни текущий коммит (`git rev-parse HEAD`) как базу для ревью.

## 2. Параллельная работа
Запусти `backend-dev` и `qa-engineer` одновременно, каждому — его часть плана и общие договорённости о стыке. Если этап затрагивает интерфейс — так же парой `frontend-dev` и `frontend-qa`; если меняются тексты для пользователей API (`README.md`, `examples/`, `/developers`, `/llms.txt`) — `tech-writer`. Зоны файлов не пересекаются (см. `CLAUDE.md`). Дождись всех отчётов.

## 3. Сборка
Запусти `uv run ruff check .` и `uv run pytest -q -n 12`. Если этап менял ручки или их параметры — перегенерируй схему (`uv run python -m app.cli openapi --output docs/openapi.json`) и проверь `git diff docs/openapi.json`: изменилось ровно то, что в контракте. Если менялся `frontend/` — `npm run lint`, `npm run typecheck`, `npm test` в `frontend/`. Если есть падения — разбери каждое:
- ошибка в коде → задача `backend-dev` с текстом падения;
- ошибка в тесте → задача `qa-engineer` (тесты фронтенда — `frontend-qa`, код фронтенда — `frontend-dev`);
- неясен контракт → вопрос мне, и жди ответа.
Максимум 3 круга. Если не сошлось — остановись и покажи мне, что осталось.

## 4. Ревью
Передай `reviewer` номер этапа, базовый коммит из шага 1, критерии готовности и таблицы «AC → тест» из отчётов `qa-engineer` и `frontend-qa` (непокрытый AC — замечание). Если этап меняет публичную поверхность (новые ручки и параметры, admin, лимиты, раздача статики, образ, развёртывание) — параллельно `security-reviewer` с тем же базовым коммитом; его CRITICAL и HIGH считаются как BLOCKER. Замечания BLOCKER и MAJOR раздай владельцам зон дословно, затем повтори шаг 3 и ревью. Максимум 2 круга ревью.

## 4а. Проверка на живых данных
Если этап менял адаптеры источников, синхронизацию или загрузку — `/sync-check <rover>` на базе разработки (запросы уже одобрены в плане; если нет — спроси). Новые причуды источника — в отчёт и в шаг 5.

## 4б. Интерфейс глазами
Если этап менял `frontend/` или `design/`: собери фронтенд (`npm run build` в `frontend/`), открой изменённые экраны во встроенном браузере по HTTP (`file://` показывается как снимок без скриптов), проверь консоль и все состояния (загрузка, пусто, ошибка), сними скриншоты и приложи к итогу. Макеты из `design/` без подключения к API явно называй статичными.

## 5. Документы
- Отметь `[x]` выполненные пункты этапа в `docs/PLAN.md` и добавь строку в «Журнал этапов».
- Если по ходу выяснились факты об источниках — обнови `docs/DATA-SOURCES.md` (снимай пометку «не проверено» только с доказательством из фикстуры).
- `docs/API.md` меняй только с моего согласия.
- Если этап виден пользователям API — `tech-writer` обновляет `README.md` и `examples/` (если не сделал на шаге 2).
