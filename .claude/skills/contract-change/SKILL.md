Ты — тимлид. Контракты (`docs/API.md` для v2, `docs/LEGACY-API.md` для v1) — источник правды; без моего подтверждения их не меняют. Изменение: $ARGUMENTS

## 1. Черновик — и стоп
- Прочитай раздел контракта, который меняется, и связанные места (`docs/ARCHITECTURE.md`, `docs/PLAN.md`).
- Если изменение небольшое (новый параметр, поле, код ответа) — сам набросай правку. Если затрагивает модель данных, несколько ручек или производительность — запусти `architect` (сначала `/budget before architect ...`).
- Покажи мне: точный текст правки контракта (как diff), совместимость (ломает ли существующих клиентов v2; для v1 — любое отступление от старого API только как новая строка в таблице расхождений `LEGACY-API.md`), что меняется в БД, какие тесты нужны.
- **Жди «ок»** на текст контракта.

## 2. Контракт
Внеси одобренный текст в `docs/API.md` (или `docs/LEGACY-API.md`) слово в слово.

## 3. Реализация и тесты
Параллельно: `backend-dev` — реализация по новому тексту; `qa-engineer` — тесты по нему же (не по коду); если затронут фронтенд — `frontend-dev` и `frontend-qa`. Передай каждому точный текст правки и договорённости о стыке.

## 4. Схема OpenAPI
- `uv run python -m app.cli openapi --output docs/openapi.json`
- `git diff docs/openapi.json` — изменилось ровно то, что в контракте. Лишние изменения схемы — вопрос к `backend-dev`.
- `uv run pytest -q tests/api/test_openapi_snapshot.py` — снимок совпадает.

## 5. Сборка и ревью
`uv run ruff check .`, `uv run pytest -q -n 12`; затем `reviewer`. Если меняется публичная поверхность (новые параметры, ручки, лимиты) — ещё `security-reviewer`.

## 6. Документация для пользователей
Если изменение видно клиентам — `tech-writer`: `README.md`, `examples/`, готовые тексты для `/developers` и `/llms.txt` (вставляет `backend-dev`). Прогон примеров против локального сервера.

## 7. Итог
Что изменилось в контракте, где реализовано, какие тесты, расхождения, найденные по ходу. Предложи сообщение коммита (`/commit-msg`).
