Ты тимлид. Дефект: $ARGUMENTS. Цель — минимальное исправление с тестом, без расползания объёма.

## 1. Разбор — без правок
- Воспроизведи: запрос к локальному серверу (`127.0.0.1:8000`, база `mars`), строка лога, тест. Продакшен не трогай (для него `/prod-status`). Если причина неочевидна — `debugger` (разбор без правок).
- Определи, кто не прав: **код**, **тест**, **контракт** (`docs/API.md`, `docs/LEGACY-API.md`) или **источник** (формат фида изменился). Если расходятся документ и код — скажи мне, сам не выбирай. Нужно изменение контракта — `/contract-change` и моё «ок».
- Оцени серьёзность: теряются или портятся данные, ломается совместимость v1, видно клиентам, безопасность (тогда `security-reviewer`).
- Покажи мне: причина, масштаб, план исправления в 3–5 строк, файлы и роли. Если исправление небольшое и очевидное — иди дальше, иначе **жди «ок»**.

## 2. Тест, который падает
`qa-engineer` (или `frontend-qa`) пишет тест на дефект по контракту: он должен падать на текущем коде. В задаче — вход, ожидаемое и фактическое, точные имена. Без падающего теста исправление не начинай (исключение — визуальный дефект: шаги воспроизведения для `/ui-check`).

## 3. Исправление
`backend-dev` (или `frontend-dev`) делает минимальную правку в своей зоне. Рефакторинг по пути не нужен; побочные находки — в отчёт.

## 4. Проверка
`uv run ruff check .`, `uv run pytest -q -n 12` (для фронтенда `npm run lint`, `npm run typecheck`, `npm test`). Новый тест зелёный, остальные целы. Падение — разбор по владельцу, максимум 2 круга, потом покажи мне.

## 5. Ревью
Дефект небольшой — смотришь дифф сам; затрагивает контракт, данные, миграции или безопасность — `reviewer` (и `security-reviewer`), с базовым коммитом и ссылкой на падающий тест.

## 6. Итог
Что было не так и почему, что исправлено, какой тест добавлен, результаты прогонов, нужна ли выкладка (`/release`) и пересчёт данных. Сообщение коммита — `/commit-msg`; коммит только после моего «ок». Заметный дефект — одной строкой в «Журнал этапов» `docs/PLAN.md`.
